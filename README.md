# Place4Market: вёрстка сайта и админки (вариант C)

PHP 8+, без фреймворков. Стили на CSS-переменных, JS на vanilla. Отступы табами.

## Запуск

```
php -S localhost:8000
```

- Сайт: http://localhost:8000/
- Админка: http://localhost:8000/admin/

## Языки

- Язык берётся из `?lang=en|sr-latn|sr-cyrl`, затем запоминается в cookie, по умолчанию `en`.
- Все внутренние ссылки строятся через `url('page.php', [...])` (внутри `lang_link()`), переключатель языка — через `lang_url()`. Чтобы перейти на SEO-адреса (`/sr/oglasi/...`), меняются только эти две функции + `.htaccess`.
- В `<head>` уже есть `hreflang` для всех трёх версий.
- Тексты интерфейса: `t('key')`, множественное число: `tp('cat.count', $n)` (сербские формы 1 / 2–4 / 5+).
- **Кириллица генерируется из латиницы:** правите `sr-latn.php`, затем `php source/lang/build-cyrillic.php`. Аббревиатуры, бренды и `{плейсхолдеры}` остаются латиницей (список исключений в `sr_cyr()`).
- Пользовательский контент (заголовки, описания, сообщения) хранится как `['en' => …, 'sr' => …]`, кириллица делается на лету через `tc()`.
- Тексты информационных страниц (о нас, помощь, безопасность, условия, приватность) лежат так же, в `source/inc/content/*.php`, а не в языковых файлах: это контент, его заменят целиком после семантического ядра. Почту и адреса в эти тексты не пишем — транслитерация их испортит.

## Данные

База — MariaDB 10.11 (как на хостинге). Страницы и хелперы получают данные только через функции `source/inc/repo.php` (`find_listing()`, `search_listings()`, `count_listings()`, `user()`, `conversations()`, `reports()`…) и сами запросов не делают.

- Объявление — массив `id, category (slug), user_id, status, title, description, lang, price, currency, negotiable, city, created, views, favorites, messages, condition, attrs, reject_reason (ключ), reject_comment, expires, sorted, phone, show_phone, images, videos, photos`; пользователь — `id, name, email, phone, city, role, status, verified, registered, last_active`. Списки идут от новых к старым.
- Тексты пользователей хранятся как написаны, с языком автора (`lang`: `sr-latn`, `sr-cyrl`, `en`). Выводятся через `user_text()` (`listing_title()`, `listing_description()`): сербский текст следует за алфавитом страницы (латиница ↔ кириллица), английский остаётся как есть, перевода нет. `tc()` — только для текстов сайта (`['en' => …, 'sr' => …]`).
- Поиск идёт по `search_text` — тому же тексту латиницей (`sr_lat()`), поэтому запрос на любом алфавите находит оба; сравнение без учёта регистра и диакритики (`cacak` находит `Čačak`).
- Даты в БД в UTC, на страницы приходят во времени сайта (`db_local()`, `db_utc()` в `db.php`).
- Текущий пользователь — `current_user_id()` (из сессии), в админке — `$currentAdmin`; `is_staff()` — модератор или админ, `is_admin()` — только админ (журнал).

### Настройки и подключение

Пароль от БД лежит не в репозитории и не в `public_html`. `config()` ищет файл настроек по порядку: переменная окружения `P4M_CONFIG` → `config/local.php` в проекте (локально, закрыт в `.gitignore`) → `app-config.php` рядом с `public_html` (хостинг). Файл возвращает массив:

```php
<?php
return [
	'db' => ['host' => 'localhost', 'port' => 3306, 'name' => 'placemar_p4m', 'user' => 'placemar_p4m', 'pass' => '…'],
	// необязательно: куда слать критичные ошибки (одно или оба)
	'alerts' => ['email' => 'dev@example.com', 'telegram' => ['token' => '…', 'chat_id' => '…']],
	// необязательно: отправитель писем и способ ('mail' | 'log')
	'mail' => ['from' => 'noreply@place4market.com', 'from_name' => 'Place4Market'],
];
```

`config()` и `db_connect()` лежат в `config.php`, его подключает `log.php`: журналу база нужна раньше остального кода (и в `js-error.php`). Сбой подключения или запроса — исключение: оно уходит в журнал (`critical`), посетитель видит страницу 500 с кодом.

### Схема, миграции, демо-данные

```
php source/db/migrate.php         # применить новые миграции
php source/db/seed.php --reset    # заменить данные на демо (даты — от момента запуска)
php source/db/cron.php            # обслуживание, на хостинге — раз в час из cron панели
```

- На хостинге SSH нет: для прода миграция выгружается в SQL-файл (`temp/prod-NNN.sql`: SQL миграции + `INSERT INTO schema_migrations`) и импортируется через phpMyAdmin перед пушем кода, который её использует.
- Миграция — файл `source/db/migrations/NNN_name.php`, который возвращает SQL (PHP, а не `.sql`, чтобы сервер не отдал схему как текст, даже если не применит `.htaccess`), применяется один раз (список — таблица `schema_migrations`). Попавшую на прод миграцию не правим: изменения — новым файлом.
- Демо-данные берутся из `source/inc/mock-data.php`, id сохраняются (`listing.php?id=1048` тот же). Чтобы демо снова было «свежим», `seed.php --reset` запускают повторно.
- Скрипты работают только из консоли; папки `source/db/` и `config/` закрыты для веба в `.htaccess`, скрипты проверяют это и сами.
- Локально: `brew install mariadb@10.11`, `brew services start mariadb@10.11`; `sql_mode` как на хостинге — в `/opt/homebrew/etc/my.cnf.d/place4market.cnf`.

На сайте работает реальная фильтрация по тестовым данным: категория, поиск, город, цена (EUR → RSD по курсу `EUR_RATE`), состояние, «можно торговаться», сортировка, пагинация.

## Вход и аккаунты

Один аккаунт на сайт и админку; роли `user`, `moderator`, `admin` (в админку — только последние две). Логика — `source/inc/auth.php`, запросы — в `repo.php`.

- `current_user()` / `current_user_id()` — кто вошёл (`null` для гостя); `require_login()` в начале служебной страницы отправляет гостя на `auth.php?next=…` и возвращает обратно. Закрыты: профиль, избранное, сообщения, подача.
- Сессия стартует только когда нужна (есть cookie, форма или вход): гость, который просто смотрит сайт, cookie не получает. Файлы сессий на хостинге — в `app-sessions/` рядом с `public_html` (`P4M_SESSION_DIR` на другом сервере). Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` на HTTPS; id сессии меняется при входе.
- «Запомнить меня» — 30 дней: в cookie `selector:validator`, в БД только sha256 валидатора; токен меняется при каждом использовании, старый не работает. Смена или сброс пароля выходит на всех устройствах.
- Каждая форма с POST — `<?= csrf_field() ?>` и `csrf_valid()` в обработчике; выход — ссылка с `?csrf=`.
- Лимиты (`RATE_LIMITS`): вход — 5 неудачных на e-mail и 20 на IP за 15 минут; регистрация — 5 на IP в час; сброс — 3 на e-mail и 10 на IP в час; повтор письма подтверждения — 3 в час. Считаются в `rate_events` по sha256 ключа.
- Пароли — `password_hash()` (bcrypt), 8–72 символа; при входе хеш обновляется, если PHP сменил алгоритм. Время ответа одинаковое для существующего и несуществующего e-mail; сброс пароля отвечает одинаково в обоих случаях.
- Письма со ссылками: подтверждение e-mail (48 часов), сброс пароля (1 час, один раз; заодно подтверждает e-mail). В БД — только sha256 токена. Тексты — `mail.*` в языковых файлах. Отправка — `mail()` сервера от `noreply@place4market.com` (`config('mail')` меняет отправителя и способ); при `php -S` письма пишутся в `logs/mail/`.
- Сообщение после переадресации — `flash('success', '…')`, выводится под шапкой (`.flash`).
- Журнал действий (`audit`): `auth.login`, `auth.login_failed` (с хешем e-mail, без самого адреса), `auth.login_blocked`, `auth.register`, `auth.logout`, `auth.reset_requested`, `auth.password_reset`, `auth.password_changed`, `auth.email_verified`, `admin.login`, `admin.login_failed`, `admin.logout`. Действия с объявлениями, жалобами и пользователями — в разделах «Подача», «Статусы» и «Модерация».
- Заблокированный пользователь выходит на следующем запросе (`auth_init()`), его объявления скрыты; модератора и админа заблокировать нельзя.
- В демо-данных паролей нет. Задать: `php source/db/password.php <email>` (локально); для хостинга — `… --sql`, полученный `UPDATE` выполнить в phpMyAdmin.

## JS: что где

Сайт (`main.js`), всё через data-атрибуты:

| Атрибут | Что делает |
|---|---|
| `data-fav` | сердечко «в избранное» (на странице избранного + `data-fav-remove` убирает карточку) |
| `data-tabs` + `role="tab"` | вкладки; `data-tabs-hash` — открытая вкладка в адресе (`#settings`) |
| `data-pills="listId"` | фильтр по статусу в «Моих объявлениях» |
| `data-drawer-open="filters"` | фильтры выезжают слева на планшете/телефоне |
| `data-dialog-open="id"` | открыть `<dialog>` |
| `data-confirm` (+ `data-remove-target`, `data-done`) | подтверждение удаления |
| `data-gallery` | галерея: стрелки, миниатюры, клавиатура, свайп |
| `data-reveal-phone` | «Показать номер» |
| `data-share` | поделиться / скопировать ссылку |
| `data-view-toggle` | сетка / список (запоминается) |
| `data-post-form` | подача: подкатегории, фото (drag & drop, обложка, удаление, подготовка перед загрузкой), живое превью |
| `data-chat` | диалоги, отправка (Enter), быстрые ответы, поиск |

**Демо-заглушки** (убрать при подключении бэкенда): `data-toast="…"` на кнопках, `data-demo="…"` на формах и `data-toast-on/off` на переключателях показывают уведомление вместо запроса к серверу.

Фото в форме подачи готовятся в браузере сразу при добавлении (`preparePhoto()` в `main.js`), по одному, чтобы телефону хватило памяти:
- поворот по EXIF применяется, длинная сторона уменьшается до 2560 px, сохранение в JPEG 0.9 — заодно пропадают EXIF и геолокация; фото с телефона 5–12 МБ → ~1 МБ;
- файл, которому не нужно уменьшение и который не больше 1,5 МБ, уходит как есть (без повторного сжатия; метаданные с него снимет сервер);
- прозрачный PNG ложится на белый фон; больше 30 МБ, сверх 12 штук или формат, который браузер не открывает (HEIC вне Safari), — сообщение пользователю. Прочие сбои уходят в журнал через `reportError()`.

Пока фото готовится и загружается, плитка пульсирует (`.photo-item.is-busy`). Готовое фото сразу уходит на `photo-upload.php` (по одному, `fetch`), сервер обрабатывает его и возвращает id; форма отправляет только `photo_ids[]` в порядке плиток (первое — обложка). Пока загрузка идёт, отправка формы заблокирована. Уже загруженные фото (редактирование, форма с ошибкой) приходят в `data-photos` списка.

## SEO

Каждая страница до подключения `header.php` задаёт в `$page`: `title`, `description`, `canonical` (`[путь, параметры]` без языка), `robots`, `schema[]` (JSON-LD), `og_type`/`og`. Тег `<head>` собирает `seo_head()` из `source/inc/seo.php`. На страницах с `noindex` (служебные, выдача с поиском/фильтрами/сортировкой) canonical и hreflang не выводятся.

Пока идёт разработка, сайт закрыт от индексации заголовком `X-Robots-Tag: noindex, nofollow` — в `.htaccess` и в `source/inc/bootstrap.php` (блоки `DEV-ONLY`, снять оба при запуске).

## Журнал ошибок и действий

`source/inc/log.php` подключается первым в обоих bootstrap и ловит всё, что падает дальше: предупреждения PHP, необработанные исключения, фатальные ошибки (в том числе нехватку памяти и ошибки разбора). Ошибки JS приходят из `main.js` и `admin.js` на `js-error.php`.

```php
log_event('error', 'Mail not sent', ['to' => $email]);    // уровни: debug, info, warning, error, critical
log_exception($e);                                         // пойманное исключение, с трассировкой
log_action('listing.delete', ['id' => 1048]);              // журнал действий (кто, что, над чем)
log_set_user($id, 'admin');                                // кто действует (в админке уже задан)
```

- Где лежит: таблица `log_entries` (с 31.10). Пишется **своим подключением** (`log_db()`), поэтому откат транзакции страницы запись не стирает. В записи: время (UTC, с миллисекундами), уровень, канал (`app`, `audit`, `http`, `js`, `db`, `mail`, `upload`, `cron`), сообщение, id запроса, метод и адрес, IP, пользователь и роль, браузер, контекст (JSON). Хранение 90 дней (`cron.php` удаляет старое).
- Запасной путь: если база недоступна (или таблицы ещё нет), запись уходит в файл дня — JSON на строку (`2026-10-29.log`), на хостинге в `app-logs/` рядом с `public_html`, при `php -S` — в `logs/` проекта (в `.gitignore`), на другом сервере — по `P4M_LOG_DIR`. `cron.php` переносит такие файлы в базу (`log_import_files()`: файл переименовывается, импортируется, удаляется; при сбое остаток ждёт следующего запуска). Раздел журнала показывает, сколько файлов ждёт. Если недоступна и папка — запись уходит в журнал PHP сервера.
- **Раздел журнала в админке** — `admin/logs.php`, только для админа (`is_admin()`): фильтры по уровню (этот и выше), каналу, пользователю (id или e-mail), периоду; поиск по коду ошибки (id запроса — все записи этого запроса) или тексту сообщения и адреса; по 50 записей, подробности (контекст, IP, браузер) — раскрываются. В сайдбаре и на дашборде — число ошибок за 24 часа. История объявления (`listing-edit.php`, вкладка History) и лента дашборда — это записи `audit` (`audit_entries()`, текст строки — `audit_line()`).
- **Уведомления о критичных ошибках** (`log_alert()`): каждая запись `critical` уходит письмом и/или в Telegram по `config('alerts')`. Одна и та же ошибка (сообщение + место) — не чаще раза в 15 минут (`LOG_ALERT_PAUSE`); состояние в файле `alerts.json` рядом с журналом, поэтому работает и при упавшей базе. В письме — сообщение, место, адрес, код и ссылка на журнал с этим кодом; локально письмо пишется в `logs/mail/`. Без `alerts` в настройках уведомлений нет.
- `js-error.php` принимает не больше 30 ошибок с одного IP за 10 минут (`rate_events`).
- Пароли, токены и похожие поля (`password`, `token`, `csrf`…) в контексте и в адресах заменяются на `***`; аргументы функций в трассировку не попадают.
- При фатальной ошибке недорисованная страница заменяется страницей 500 с кодом ошибки (это id запроса, он же в заголовке `X-Request-Id`): по коду запись находится в журнале. При `php -S` на странице видна сама ошибка, на проде — нет.
- 404 тоже пишутся (канал `http`): битая ссылка с нашей же страницы — `warning`, заход извне — `info`.

## Модерация и жалобы

Новое и изменённое объявление приходит в админку со статусом `pending` (счётчик в сайдбаре). Все действия персонала — POST на `admin/moderate.php` (CSRF, `back` — на какую страницу вернуться), каждое пишется в журнал действий.

- **Одобрить** (`approve_listing()`): первое одобрение — `published_at` и `sorted_at` = сейчас (наверх выдачи), `expires_at` = +60 дней (`LISTING_DAYS`). Одобрение после правки — место в выдаче и срок сохраняются, срок продлевается, только если истёк (правка не даёт бесплатного «поднять»). Продавцу — письмо `mail.listing_approved`.
- **Отклонить** (`reject_listing()`): причина — ключ (`reject_reasons()` в админке, `rj.<ключ>` на языке продавца) и сообщение (`reject_comment`). Продавец видит их в профиле, письмо `mail.listing_rejected` со ссылкой на правку — если не снята галочка. Исправленное объявление снова уходит на модерацию.
- **Удалить** (`staff_delete_listing()`): как удаление автором — статус `deleted`, фото с файлами удаляются, строка остаётся для переписки.
- Массово: отметить строки в списке → «Approve» / «Reject» / «Delete» (`form[data-bulk-form]` отправляет `ids[]` отмеченных видимых строк, диалог отклонения получает их через `data-bulk-ids`). Из меню строки и из карточки объявления — то же для одного.
- **Блокировка** пользователя (`block_user()`) — из карточки объявления (вкладка Seller), страницы пользователя или по жалобе.
- Письма продавцу — `notify_seller()`: на языке, на котором написано объявление (`in_lang()`), ссылки ведут на эту же языковую версию. Сбой отправки пишется в журнал и модерацию не останавливает.

Жалобы: на сайте — ссылка «Пожаловаться» на чужом опубликованном объявлении (гостя просит войти), диалог отправляет на `report.php`. Причины — ключи `r.<ключ>`, одна открытая жалоба от пользователя на объявление (повтор — та же благодарность, без новой записи), не больше 10 в час (`RATE_LIMITS['report']`). В админке (`reports.php`): «Review» → «Mark in review» или решение с внутренней заметкой. Решение действует сразу: «Ask the seller to edit» — объявление отклоняется с сообщением продавцу; «Remove» — удаляется; «Remove and block» — удаляется, продавец блокируется; «Dismiss» — ничего. Кто и как решил — в таблице жалоб.

Журнал действий: `listing.approve`, `listing.reject`, `listing.remove`, `admin.user_block`, `admin.user_unblock`, `report.create`, `report.review`, `report.resolve` (в контексте `listing_id`, `report_id`, причина или решение).

Ещё демо в админке: сохранение правок объявления и фото персоналом, роли и массовые действия на странице пользователей, категории, настройки, экспорт CSV, пагинация списков (все строки на одной странице, фильтры в браузере).

## Фото объявлений

Правила (размеры, качество, обработка) — в `CLAUDE.md`, раздел 2. У объявления в `images` лежит список фото, первое — обложка:

```php
['path' => 'img/demo/1048-1', 'color' => '#938e85', 'sizes' => [1920 => [1920, 1280], 960 => [960, 640], 480 => [480, 320], 320 => [320, 213], 200 => [200, 133]]]
```

Файлы — `source/<path>/<размер>.webp`, размер = длинная сторона. Выводит их `photo($photo, $sizes, $opts)` (`helpers.php`, общий для сайта и админки):
- размеры: 1920 / 960 / 480 / 320 / 200 (320 — карточки на обычных экранах); в `srcset` все размеры (или до `max`), `width`/`height` для пропорций, средний цвет фоном до загрузки — CLS 0;
- `sizes` по месту — `PHOTO_SIZES` в `site.php` (карточка, галерея, миниатюра, строка, чат), потолок размера — `PHOTO_MAX`; в галерее фото вписывается целиком (`pic--contain`), `photo_sizes_contain()` уменьшает `sizes` для вертикальных;
- `lazy` по умолчанию; у первых четырёх карточек выдачи и главной — без него (`$cardEager`), у первой и у главного фото объявления — `fetchpriority="high"` (`$cardPriority`, `priority`).

На странице объявления обложка уходит в `og:image`, все фото — в `Product.image`. Без фото выводится заглушка с иконкой категории (`placeholder()`).

Видео (`videos` у объявления: `path`, `file`, `width`, `height`, `duration`, `bytes`, `poster` — фото того же вида) встаёт в галерею вторым слайдом, после обложки:
- фасад `button[data-video]`: постер через `photo()`, кнопка и длительность (`video_time()`); `<video>` создаётся только по нажатию (`initVideos()` в `main.js`), до этого грузится лишь постер, и только когда слайд открыт;
- при переходе на другой слайд ролик ставится на паузу, стрелки и свайп на плеере не листают галерею; ошибки файла или кодека уходят в журнал;
- в `Product` — `subjectOf` с `VideoObject` (постер, файл, длительность).

### Загрузка и обработка (`source/inc/media.php`)

- Фото загружается до отправки формы и ждёт её без объявления (`listing_id` NULL, владелец — `user_id`); неиспользованные удаляются через сутки (`take_stale_photos()`: `source/db/cron.php` и изредка при загрузке, как запасной путь). При сохранении объявления `set_listing_photos()` ставит фото в нужном порядке, снятые удаляются вместе с файлами.
- Проверки: тип по содержимому (JPEG, PNG, WebP), до 15 МБ, до 16 Мп, не меньше 200 px по короткой стороне; JPEG поворачивается по EXIF; прозрачность — на белом; метаданные не переносятся (файл перекодируется).
- Размеры 1920 / 960 / 480 / 320 / 200 с качеством из CLAUDE.md, без увеличения: фото меньше 1920 хранит свой размер как самый крупный. Файлы — `uploads/listings/ГГГГ/ММ/<случайное>/<размер>.webp`, путь в БД от корня сайта (демо — `source/img/demo/…`).
- Сейчас — PHP GD, сразу при загрузке (хостинг без libvips; браузер присылает ≤ 2560 px, это около секунды). На новом сервере `process_photo()` переходит на libvips и очередь, остальной код не меняется. Видео ждёт ffmpeg (переезд).
- Лимиты PHP на хостинге: `upload_max_filesize` ≥ 16M, `post_max_size` ≥ 20M, `memory_limit` ≥ 256M (запрос больше `post_max_size` отвечает «слишком большой файл» и пишется в журнал). Локально: `php -d upload_max_filesize=16M -d post_max_size=20M -S localhost:8000`.

### Подача и редактирование (`post.php`)

- Только для вошедших; `?id=` — своё объявление (чужое — 404). Новое и изменённое объявление уходят на модерацию (`pending`), в поиске и у гостей его нет; автор и модераторы видят его со штампом «не опубликовано» (`noindex`).
- Проверки: подкатегория внутри категории, заголовок 3–80, описание 10–3000, состояние, цена или «по договорённости», город, телефон, до 12 своих фото, согласие с условиями. Язык текста определяется сам (`detect_text_lang()`): кириллица → `sr-cyrl`, č/ć/ž/š/đ → `sr-latn`, иначе по языку страницы.
- У объявления свой телефон и признак «показывать»; без телефона кнопки звонка скрыты. Журнал действий: `listing.create`, `listing.update`, `listing.draft`.
- **Черновик** (кнопка `action=draft`, `formnovalidate`; только у нового объявления и у черновика): обязательна лишь подкатегория, остальное сохраняется, если верно. После сохранения форма открывается снова (`?id=`); отправка черновика — обычная подача.
- **Характеристики** (`source/inc/attrs.php`): набор полей по подкатегории в `CATEGORY_ATTRS`, типы полей — `attr_fields()` (число с единицей и пределами, список, короткий текст). Все необязательные. В форме выводятся все наборы, `main.js` показывает набор выбранной подкатегории, остальные `disabled` и не отправляются. Там же — где «состояние» не спрашивается (недвижимость, услуги, работа). В БД (`attrs`, JSON) — сырые значения (`168000`, `v.diesel`); на странице объявления `listing_details()` выводит состояние и характеристики с единицами и переводом. Новое поле: ключ в `attr_fields()` и подкатегории + `a.<ключ>` и `v.<вариант>` в языковых файлах.

### Статусы и «Мои объявления» (`profile.php`)

- `draft` → `pending` (модерация) → `active` / `rejected`; `active` ↔ `inactive` (автор снял / вернул); `active` → `expired` по `expires_at` (`LISTING_DAYS` = 60 с одобрения); `deleted` — удалено автором: строка остаётся для переписки и админки, фото удаляются вместе с файлами, избранное очищается. Удалённое видят только модераторы.
- Опубликовано = `LISTING_LIVE` (`active` и срок не истёк): по нему строятся выдача, карта сайта, избранное. Активное с истёкшим сроком сразу читается как `expired` (`listing_from_row()`), `cron.php` потом исправляет статус в БД.
- Порядок выдачи «Новые» — `sorted_at`: время публикации, «Поднять» переносит его на «сейчас» (не чаще раза в `RAISE_HOURS` = 24 ч, пока нельзя — кнопки нет). Продление истёкшего — ещё 60 дней и наверх.
- Действия — POST на `profile.php` (`id`, `action` = `raise` / `deactivate` / `activate` / `renew` / `delete`, CSRF), функции в `repo.php` меняют только своё объявление в нужном статусе. Журнал действий: `listing.<action>`.

Демо-фото и демо-видео — бесплатные с Pexels, обработаны так же, как будет обрабатывать сервер; списки и скрипт — локально в `doc/tools/demo-photos.py`. С бэкендом `demo-photos.php`, `demo-videos.php` и `source/img/demo/` удаляются, данные идут из БД.

## Ассеты и кэш

CSS, JS и иконки подключаются через `asset('css/site.css')` → `source/css/site.css?v=<дата изменения>`, поэтому их можно кэшировать на год. Шрифты подключаются без версии: изменённый шрифт кладём под новым именем.

CSS и JS минифицируются при деплое (esbuild в `.github/workflows/deploy.yml`), в репозитории лежат читаемые исходники. Локально (`php -S`) работают исходники как есть.

## Адаптив

Сайт: десктоп ≥1440 (базовые стили), ноутбук ≤1439, планшет ≤1023, телефон ≤767; телефон рисуется под 360 и держится до 320. Админка: десктоп ≥1024 и мобильный ≤1023.

## Цвета и шрифты

`source/css/variables.css`: терракота `--color-accent`, олива `--color-olive`, морской `--color-sea`, бумажный фон `--color-bg`. Шрифты Lora (заголовки, цены) и Source Sans 3 (текст), обе с кириллицей, лежат в `source/fonts/` (`@font-face` в начале `variables.css`, Google Fonts не используется). Браузер грузит только нужные наборы символов; запасные шрифты подогнаны по метрикам, чтобы при загрузке ничего не прыгало. Для текста на светлом фоне используется `--color-accent-ink` (контраст AA), основной терракотовый — для кнопок с белым текстом.

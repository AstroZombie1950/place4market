# Place4Market

Доска объявлений для Сербии: сайт на трёх языках (сербский латиницей и кириллицей, английский) и админка (английский / русский).
PHP 8.5 без фреймворков, MariaDB 10.11, стили на CSS-переменных, JS на vanilla. Отступы табами. Прод — https://place4market.com (сервер AdriaHost, DirectAdmin + OpenLiteSpeed; деплой — пуш в `main`).

## Запуск

```
php -S localhost:8000 route.php
```

`route.php` — маршрутизатор человекочитаемых адресов (на сервере его подключает `.htaccess`); без него открывается только главная. Загрузка фото: `php -d upload_max_filesize=16M -d post_max_size=20M -S localhost:8000 route.php`.

- Сайт: http://localhost:8000/ (сербский латиницей), /cir/ (кириллица), /en/ (английский)
- Админка: http://localhost:8000/admin/

## Языки и адреса

Основной язык — сербский латиницей, в корне; кириллица — `/cir/`, английский — `/en/` (этап 5, 05.11). Язык задаётся только адресом: cookie и язык браузера не учитываются, у каждой версии свой адрес для людей и поисковиков (`hreflang` `sr-Latn` / `sr-Cyrl` / `en`, `x-default` — латиница).

| Страница | Латиница | Кириллица | Английский |
|---|---|---|---|
| Главная | `/` | `/cir/` | `/en/` |
| Выдача, категория | `/oglasi`, `/oglasi/vozila/automobili` | `/cir/oglasi/…` | `/en/listings/vehicles/cars` |
| Объявление | `/oglas/vw-golf-7-1-6-tdi-2016-1048` | `/cir/oglas/…` | `/en/listing/…` |
| Продавец | `/prodavac/12` | `/cir/prodavac/12` | `/en/seller/12` |
| Информационные | `/o-nama`, `/pomoc`, `/bezbednost`, `/uslovi-koriscenja`, `/privatnost`, `/kontakt` | `/cir/…` | `/en/about`, `/en/help`, `/en/safety`, `/en/terms`, `/en/privacy`, `/en/contact` |
| Служебные | `/prijava`, `/nova-lozinka`, `/potvrda`, `/profil`, `/omiljeno`, `/poruke`, `/postavi-oglas` | `/cir/…` | `/en/login`, `/en/reset-password`, `/en/verify`, `/en/profile`, `/en/favorites`, `/en/messages`, `/en/post-ad` |

- **Ссылки** — только `url('page.php', [...])` (внутри `lang_link()`): адрес всегда от корня, слова страницы — `page_routes()` в `i18n.php`. Категория — параметр `cat` (ключ = английский slug), объявление — `listing_url($listing)` (слова из названия + id), продавец — `id`; остальные параметры (`q`, `city`, `sort`, `page`…) — в строке запроса. Переключатель языка — `lang_url()` (тот же адрес в другом языке, фильтры сохраняются).
- **Служебные адреса** (`favorite.php`, `phone.php`, `view.php`, `report.php`, `photo-upload.php`, `saved-search.php`, `logout.php`, `js-error.php`, `sitemap.php`) остаются `.php`, язык — `?lang=` (кроме основного).
- **Как это работает:** `.htaccess` отправляет всё, что не файл и не папка, в `route.php`; он читает адрес (`route_match()`: язык по префиксу, страница по первому слову, остальное — параметры), кладёт параметры в `$_GET` как раньше (`id`, `cat`), язык и страницу — в `$GLOBALS['__route']` (`lang()`, `current_script()`), и подключает страницу. Неизвестный адрес — наша 404 на языке префикса (вместо 404 сервера). Слова категории `route_resolve()` ищет в базе (`slug_sr` / `slug`, затем прежние — `category_old_slugs`).
- **Один адрес на страницу (301, `enforce_url()`):** старые `page.php?…&lang=…`, `?lang=` на новом адресе, другой регистр, слэш в конце, слово другого языка (`/oglasi/vehicles`), прежнее название объявления, прежний slug категории — всё уходит на точный адрес. Только GET; POST не перенаправляется. Корни языков — со слэшем (`/en/`), остальное — без.
- **Объявление:** слова — `url_slug()` из названия как написано (латиница без диакритики, `đ` → `dj`, кириллица переводится, до 70 символов по границе слова), одинаковые во всех языках; страница находится по id, поэтому новое название меняет адрес, а старый отвечает 301.
- **Категории:** `slug` — ключ (`?cat=`, сохранённые поиски) и английское слово, `slug_sr` — сербское (латиница и кириллица). Правятся в админке (Categories → Address words); смена слова записывает прежнее в `category_old_slugs` — старый адрес отвечает 301. Сохранённые поиски хранят английский slug: его менять не стоит.
- **Новая страница:** строка в `page_routes()` (сербское и английское слово). Сменить слово страницы — старое в `route_aliases()`, иначе старые адреса станут 404.
- Тексты интерфейса: `t('key')`, множественное число: `tp('cat.count', $n)` (сербские формы 1 / 2–4 / 5+).
- **Кириллица генерируется из латиницы:** правите `sr-latn.php`, затем `php source/lang/build-cyrillic.php`. Аббревиатуры, бренды и `{плейсхолдеры}` остаются латиницей (список исключений в `sr_cyr()`).
- Пользовательский контент (заголовки, описания, сообщения) хранится как написан, с языком автора, и выводится через `user_text()` (подробно — «Данные»). `tc()` — только для текстов сайта вида `['en' => …, 'sr' => …]`.
- Тексты информационных страниц (о нас, помощь, безопасность, условия, приватность) лежат так же, в `source/inc/content/*.php`, а не в языковых файлах: это контент, его заменят целиком после семантического ядра. Почту и адреса в эти тексты не пишем — транслитерация их испортит.

## Структура каталога и посадочные (этап 6)

Дерево утверждено 09.11 (`doc/semantics/structure.md`): 20 разделов, 163 подкатегории, 192 места, районы Beograd и Novi Sad.

- **Где лежит.** Дерево, места и районы — в базе (миграция `015_structure`, источник данных — `source/db/taxonomy.php`, по нему же работает сид). После 015 главная — база: названия, SEO и видимость правятся в админке; менять `source/db/taxonomy.php` — только вместе с новой миграцией. Сделки, виды и марки — в коде, `source/inc/taxonomy.php` (`CATEGORY_DEALS`, `CATEGORY_TYPES`, `CATEGORY_BRANDS`, `SECTION_TYPES`, `DEAL_H1`); у объявления — `deal`, `item_type`, `brand`, `district_id`, `seller_type`. Поля подкатегорий — `attrs.php` (`CATEGORY_ATTRS`, тип `bool` — галочка). Модель (`model`, автомобили, мотоциклы, тракторы) — тоже поле: свободный текст, в форме подачи стоит сразу после марки, попадает в `search_text`, на кириллической странице остаётся как написано (`'raw'`).
- **Места:** `cities.kind` (city | resort | abroad), `main_rank` 1–40 — главные (фильтры с группой «Glavna mesta», главная, посадочные); остальные — полный список общин (с Косово и Метохией) для формы подачи. В форме место вводится в поле с подсказками (`<datalist>`), сервер понимает латиницу и кириллицу (`city_by_input()`). Район — только для разделов из `DISTRICT_SECTIONS` (недвижимость) и только в городах с районами.
- **Адреса выдачи:** `/oglasi/<раздел>/<подкатегория>/<сделка>/<вид|марка>/<место>/<район>`, каждая часть необязательна (`/oglasi/nekretnine/stanovi/prodaja/beograd/zemun`, `/oglasi/vozila/automobili/volkswagen`, `/oglasi/moda/patike`, `/oglasi/posao/beograd`, `/oglasi/novi-sad`); английские — те же части по-английски (`/en/listings/real-estate/apartments/sale/belgrade/zemun`), места латиницей, у Белграда — `belgrade`. Разбор — `route_facets()` (`site.php`), сборка — `category_route_words()` (`i18n.php`). Параметры запроса важнее пути (форма фильтров шлёт новые значения); адрес выдачи канонизируется вместе с запросом: пустые поля формы и `?currency` без цены уходят 301-м, метки `utm_*`, `gclid`, `fbclid` сохраняются.
- **Посадочные:** утверждённые комбинации — таблица `landings` (миграция `016_landings`, 471 шт., спрос из `doc/semantics/structure/landings.csv`). Такая страница индексируется, пока в ней есть объявления, и попадает в карту сайта (`?part=landings`); любая другая комбинация фильтров — `noindex, follow`. Заголовок — `results_h1()` («Prodaja stanova Zemun, Beograd», «Polovni automobili Volkswagen»), описание — `meta.landing`; собственные h1, title, description и текст (этап C) — поля `landings.*_sr/_en` и `categories.h1_*`, `categories.text_*`. Под выдачей — блоки перелинковки (ниже) и SEO-текст (виден заголовок, текст — под «Više»).
- **Перелинковка (10.11).** Ссылки ставятся только на включённые посадочные, в которых есть объявления: пустая — `noindex`, вести на неё незачем. Число объявлений всех посадочных считает `landing_counts()` (`repo.php`) одним сгруппированным запросом на страницу; чипы с числом собирает `landing_links()` (`site.php`), вывод — `partials/landing-links.php`. Порядок — по спросу (`landings.demand`).
  - *Выдача и посадочная* (только индексируемые: без поиска, сортировки и прочих фильтров), `nearby_landings()`: «Popularne pretrage» — на шаг глубже (ещё одно условие: место, вид, марка, сделка, район; или те же условия в категории внутри этой: «Oglasi Beograd» → «Nekretnine Beograd»); «Slične pretrage» — рядом (то же с другим значением одного условия: другой город, марка, район, сделка; затем те же условия в другой категории: «Polovni automobili Beograd» → «Nekretnine Beograd», «Oglasi Beograd»). Соседние подкатегории — в боковой панели фильтров.
  - *Объявление:* «Pogledajte još» — посадочные, к которым оно относится (`listing_landings()`), от точной к общей: «Prodaja stanova Liman, Novi Sad» → «Prodaja stanova Novi Sad» → «Nekretnine Novi Sad» → «Oglasi Novi Sad», до 12. «Slični oglasi» — из той же подкатегории, затем раздела, затем любые; «Vidi sve» ведёт в подкатегорию.
  - *Главная:* «Popularne pretrage» под свежими объявлениями — 20 посадочных с наибольшим спросом, где есть объявления.
- **Тексты (этап C, 10.11).** Порядок: свой текст из базы, иначе шаблон. Сербский хранится латиницей, кириллическая страница переводит его через `sr_cyr()` (марки и английские слова из списка `$keep`, слова с буквами не из сербского алфавита — `Kärcher` — и сочетания из `$phrases` — «all season», «hi-fi», модели с дефисом вроде «CR-V», «C-HR», «X-Trail» — остаются латиницей; «rent a car» пишется «рент а кар»). В `$keep` с 11.11 стоят и марки и модели автомобилей из текстов посадочных (Opel, Octavia, Corolla…): побуквенно они выходили бы «Оцтавиа», «Цхевролет». ## Данные

База — MariaDB 10.11 (как на сервере). Страницы и хелперы получают данные только через функции `source/inc/repo.php` (`find_listing()`, `search_listings()`, `count_listings()`, `user()`, `conversations()`, `reports()`…) и сами запросов не делают.

- Объявление — массив `id, category (slug), user_id, status, title, description, lang, price, currency, negotiable, city, created, views, favorites, messages, condition, attrs, reject_reason (ключ), reject_comment, expires, sorted, contact (`messages` | `calls` | `both`), images, videos, photos`; пользователь — `id, name, email, phone, city, role, status, verified, registered, last_active`. Списки идут от новых к старым. `messages` — число диалогов (сколько покупателей написали), на странице — «N разговоров».
- Время на карточке и в объявлении — `listing_time()`: публикация или последнее «поднять» (`sorted`), то есть порядок ленты «Новые»; до публикации — время создания.
- Несколько объявлений сразу (диалоги, жалобы в админке) — `find_listings($ids)`: три запроса на весь список вместо трёх на строку.
- Тексты пользователей хранятся как написаны, с языком автора (`lang`: `sr-latn`, `sr-cyrl`, `en`). Выводятся через `user_text()` (`listing_title()`, `listing_description()`): сербский текст следует за алфавитом страницы (латиница ↔ кириллица), английский остаётся как есть, перевода нет. `tc()` — только для текстов сайта (`['en' => …, 'sr' => …]`).
- Поиск идёт по `search_text` — тому же тексту латиницей (`sr_lat()`), поэтому запрос на любом алфавите находит оба; сравнение без учёта регистра и диакритики (`cacak` находит `Čačak`).
- Даты в БД в UTC, на страницы приходят во времени сайта (`db_local()`, `db_utc()` в `db.php`).
- Текущий пользователь — `current_user_id()` (из сессии), в админке — `$currentAdmin`; `is_staff()` — модератор или админ, `is_admin()` — только админ (журнал).

### Схема, миграции, демо-данные

```

php source/db/seed.php --reset    # заменить данные на демо (даты — от момента запуска); на проде НЕ запускать
```

Cron на сервере (DirectAdmin → Cron Jobs пользователя `placemar`, минута `7`, остальное `*`, команда одной строкой): `/usr/local/php85/bin/php /home/placemar/domains/place4market.com/public_html/source/db/cron.php > /dev/null 2>&1`. Версию PHP указываем явно. В журнал cron пишет, только когда что-то сделал (уровень `info`, канал `cron`).

Обработчик видео (с 12.11, `source/db/media-worker.php`) — второй cron того же пользователя, **каждую минуту** (все поля `*`): `/usr/local/php85/bin/php /home/placemar/domains/place4market.com/public_html/source/db/media-worker.php > /dev/null 2>&1`. Пока его нет, видео стоят в очереди «Obrada videa…»; в журнал он пишет только когда обработал или отклонил видео (канал `video`).

- **Деплой и миграции на проде** — по SSH (`.github/workflows/deploy.yml`, сервер 85.17.188.76 с DirectAdmin и OpenLiteSpeed), в три шага: rsync заливает изменённые файлы в папку выпуска `place4market.com/release` (рядом с `public_html`, снаружи не видна) → `ssh … migrate-release` запускает `php release/source/db/migrate.php`, пока сайт работает на прежнем коде → `ssh … publish` копирует `release/` в `public_html` (только изменённые; `uploads/` и `.well-known/` не трогаются). Сбой миграции останавливает деплой до выпуска, пишется в журнал как `critical` (с уведомлением); применённые до неё остаются. Ключ деплоя (секрет `SSH_DEPLOY_KEY`) на сервере ограничен шлюзом `/usr/local/bin/p4m-deploy-gate`: только rsync в `release`, `migrate-release` и `publish` (публикация отказывает, если в `release` нет `index.php`, `.htaccess` или `source/inc/bootstrap.php`); журнал шлюза — `/home/placemar/deploy.log`. OpenLiteSpeed перечитывает `.htaccess` только после перезапуска — это делает служба `p4m-htaccess.path`, когда файл меняется.
- Запасные пути: админка → **Migrations** (только админ; список применённых и ожидающих, кнопка «Apply», счётчик ожидающих в сайдбаре; `admin.migrate` в журнале); если сама админка падает на новой схеме — `php source/db/migrate.php` на сервере по SSH (root) или SQL-файл в phpMyAdmin (`temp/prod-NNN.sql`: SQL миграции + `INSERT INTO schema_migrations`). Два запуска сразу не пересекаются (`GET_LOCK`).
- **Бэкапы** — `/usr/local/bin/p4m-backup` раз в сутки (02:30 UTC, `/etc/cron.d/p4m-backup`): дамп базы одной транзакцией (`db.sql.zst`, проверяется, что дописан до конца), `app-config.php` и снимок `uploads/` (rsync с жёсткими ссылками на прошлый снимок) в `/var/backups/p4m/` (только root), хранение 14 дней. Итог — запись `Backup done` в журнале (канал `backup`), сбой — `critical` с уведомлением. Восстановить базу: `zstd -dc /var/backups/p4m/<день>/db.sql.zst | mysql placemar_p4m`. Копии вне сервера пока нет. Итог `Backup done` несёт `db_bytes` и `total_bytes` (с 12.11; все копии в байтах) — их показывает админка → «Хранилище и расходы».
- **MariaDB на сервере** — свои настройки в `/etc/my.cnf.d/p4m-tuning.cnf` (файлы DirectAdmin не трогаем): только `127.0.0.1`, `innodb_buffer_pool_size` 1G, медленные запросы дольше 1 с — в `/var/lib/mysql/slow.log` (ротация — `/etc/logrotate.d/p4m-mysql-slow`), utf8mb4 по умолчанию.
- **Миграция совместима с прежним кодом:** новые таблицы, новые колонки со значением по умолчанию. Код и схема меняются не в один миг (миграции применяются раньше, чем новый код попадает на сайт, — какое-то время прежний код работает с новой схемой), поэтому удаление или переименование колонки — в два деплоя: сначала код перестаёт её использовать, потом миграция.
- Миграция — файл `source/db/migrations/NNN_name.php`, который возвращает SQL (PHP, а не `.sql`, чтобы сервер не отдал схему как текст, даже если не применит `.htaccess`), применяется один раз (список — таблица `schema_migrations`). Попавшую на прод миграцию не правим: изменения — новым файлом.

## Вход и аккаунты

Один аккаунт на сайт и админку; роли `user`, `moderator`, `admin` (в админку — только последние две). Логика — `source/inc/auth.php`, запросы — в `repo.php`.

- `current_user()` / `current_user_id()` — кто вошёл (`null` для гостя); `require_login()` в начале служебной страницы отправляет гостя на `auth.php?next=…` и возвращает обратно. Закрыты: профиль, избранное, сообщения, подача.
- Сессия стартует только когда нужна (есть cookie, форма или вход): гость, который просто смотрит сайт, cookie не получает. Файлы сессий на сервере — в `app-sessions/` рядом с `public_html` (другое место — `P4M_SESSION_DIR`). Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` на HTTPS; id сессии меняется при входе. Параметры запроса чистит `request_clean()` (`helpers.php`, из обоих bootstrap): в `$_GET` остаются только строки (`?deal[]=x` раньше давал 500), текст `$_GET` и `$_POST` приводится к корректному UTF-8. Массивы в запросе страницы не принимают; формы с массивами (`attrs[]`, `notify[]`, `ids[]`) — только POST. Сессия без запросов дольше 2 суток (`SESSION_IDLE_SECONDS`) заканчивается на сервере (`auth_init()`, дальше входит «запомнить меня»), её файл удаляет `cron.php`: встроенная чистка PHP на сервере срабатывает раз на 1000 запросов.
- «Запомнить меня» — 30 дней: в cookie `selector:validator`, в БД только sha256 валидатора; токен меняется при каждом использовании, старый не работает. Смена или сброс пароля выходит на всех устройствах.
- Каждая форма с POST — `<?= csrf_field() ?>` и `csrf_valid()` в обработчике; выход — ссылка с `?csrf=`.
- Куда вернуть после входа (`next`) — только путь этого сайта (`safe_next()`): без `//`, обратного слэша и управляющих символов (браузер выбрасывает табуляцию из адреса, и `/\t/evil.com` стал бы `//evil.com`).
- Абсолютные ссылки (письма, canonical, sitemap) — `site_url()`: всегда `https://place4market.com`, заголовок Host запроса не учитывается (иначе подделанный Host попал бы в ссылку сброса пароля); только `php -S` оставляет свой адрес.
- Лимиты (`RATE_LIMITS`): вход — 5 неудачных на e-mail и 20 на IP за 15 минут; регистрация — 5 на IP в час; сброс — 3 на e-mail и 10 на IP в час; повтор письма подтверждения — 3 в час. Считаются в `rate_events` по sha256 ключа.
- Пароли — `password_hash()` (bcrypt), 8–72 символа; при входе хеш обновляется, если PHP сменил алгоритм. Время ответа одинаковое для существующего и несуществующего e-mail; сброс пароля отвечает одинаково в обоих случаях.
- **Отправка писем (11.11)** — `send_mail()` (`mail.php`), способ — `config('mail')['transport']`: `log` (локально — файлы в `logs/mail/`), `mail` (по умолчанию на сервере: exim, DKIM, SPF), `smtp` — напрямую в почтовый сервис, свой клиент `smtp_send()` без библиотек: STARTTLS (587) или TLS (465), сертификат проверяется, AUTH PLAIN / LOGIN, тело в quoted-printable по строкам (любой сервер примет, строки ≤ 76), точки в начале строк удваиваются. **Запасной путь:** если сервис не ответил или отказал до приёма письма (соединение, TLS, вход, отправитель) — письмо уходит через `mail()`, в журнале `warning` «SMTP unavailable, sent by mail()»; отказ получателю или сбой во время DATA — `error` без повтора (иначе письмо может прийти дважды). Пароль сервиса и текст письма в журнал не пишутся. Оповещения журнала (`log_alert()`) нарочно идут через `mail()`: они должны дойти и при сбое сервиса. Проверено 11.11: локально на тестовом SMTP-сервере (STARTTLS, TLS, неверный пароль, отказ получателю, сервер недоступен; тело доходит байт в байт), на проде — письмо на Gmail через SMTP сервера (587, вход под `support@`, TLS 1.3, DKIM, «250 OK»). Exim в DirectAdmin не даёт ящику отправлять от чужого адреса (`noreply@` под входом `support@` — 550), поэтому для SMTP своего сервера `from` = адрес ящика; у SES и других сервисов отправка разрешается для всего домена после подтверждения.
- **Сроки хранения (11.11)** — `cron.php` раз в час: `purge_deleted_listings()` — у объявлений, удалённых больше `RETENTION_MONTHS` (12) месяцев назад (по `updated_at`), стираются заголовок, описание, поля, телефон и заметки модерации; строка остаётся, потому что на неё ссылается переписка второй стороны (удаление строки удалило бы и её каскадом), в чате вместо заголовка — «Oglas je uklonjen» (`listing_title()`, `l.removed`), в админке — «без названия»; фото удаляются ещё при удалении объявления. `delete_old_contact_messages()` — сообщения с `contact.php` старше 12 месяцев; `delete_old_reports()` — жалобы, закрытые больше 12 месяцев назад (открытые ждут модератора). Итог — в записи «Cron: maintenance done» (`listings_scrubbed`, `contact_deleted`, `reports_deleted`). Эти сроки, журнал (90 дней) и бэкапы (14 дней) записаны в политике конфиденциальности, раздел 7: меняем вместе.
- **Юридические тексты (11.11)** — `source/inc/content/privacy.php` (политика конфиденциальности с разделом о cookies) и `terms.php` (условия), sr + en, кириллица через `tc()`; написаны по тому, что сайт делает на самом деле (данные, cookies, сроки, обработчики), реквизиты оператора и сроки хранения — заглушки в `[скобках]` для заказчика и юриста. При изменении функционала (новые данные, cookies, внешние сервисы — почта, облако; числа из админки: срок объявления, число фото) тексты правим вместе с кодом.
- **Почта поддержки** — настоящий ящик `support@place4market.com` (создан 11.11 через API DirectAdmin; IMAP `mail.place4market.com:993` SSL, SMTP `:587` STARTTLS, веб-почта — DirectAdmin → E-mail Accounts). Пароль — `/root/p4m-support-mailbox.txt` на сервере (только root). `SITE_EMAIL` (`seo.php`) и настройка «Support email» в админке (сообщения с `contact.php`) указывают на него.

Отправка — `mail()` сервера от `noreply@place4market.com` (`config('mail')` меняет отправителя и способ); при `php -S` письма пишутся в `logs/mail/`.

Вывод — `phone_format()` («+381 64 123 4567»). Так же в регистрации, профиле и карточке пользователя в админке. Миграция `031` привела к этому виду старые номера, не сербские стёрла вместе с отметкой «подтверждён».

Истёкшие чистит `cron.php`.

Цена (12.11): SMS в Сербию $0,41 + $0,05 за успешную проверку.

Журнал: `review.create`, `review.delete`, `admin.review_delete`.

- В демо-данных паролей нет. Задать: `php source/db/password.php <email>` (локально или на сервере по SSH); `… --sql` — только напечатать `UPDATE` (например, для phpMyAdmin).

**Общее поведение (12.11):**
- **Выпадающие списки** — `select.js`, подключён на сайте и в админке перед основным скриптом. Каждый `<select>` получает кнопку и список в стиле сайта; сам `<select>` остаётся в странице как значение формы (его по-прежнему заполняют, отключают и слушают `input` / `change`, значение из кода показывается сразу). От 12 пунктов — поле поиска (латиница, кириллица, без диакритики), на телефоне такой список открывается на весь экран. `select[data-plain]` — оставить как рисует браузер. Тексты — `data-select-*` у `<body>`, стили — блок «Drop-down lists» в `site.css` и `admin.css`.
- **Многострочные поля** растут с текстом до `data-max-rows` строк (по умолчанию 10, на телефоне 8), дальше прокрутка внутри; руками не тянутся (`autosize()` в `main.js`, тот же код в `admin.js`).
- **Ошибки форм** (`initValidation()` в `main.js`, только сайт): вместо подсказок браузера — текст под полем (`[data-error]` в `.field`, создаётся сам). Правила остаются в разметке (`required`, `minlength`, `type="email"`). Кнопка с `formnovalidate` и `form[data-no-validation]` проверку пропускают; `form[data-live-validation]` (подача) проверяет поле при уходе из него.
- **Сворачивание:** любой `<details>` открывается и закрывается с анимацией высоты (`initDetails()`), пока закрывается — класс `.is-closing`.
- **Значки после имени** — `trust_marks($user)` (`site.php`), выводится внутри элемента с именем: печать с галочкой у администратора (`role = admin`), письмо — подтверждён e-mail, трубка — подтверждён телефон. Пояснение — `data-tip`, открывается по наведению, фокусу и нажатию (стили «Trust marks» в `site.css`). Стоят в объявлении, на странице продавца, в своём профиле и в шапке диалога.
- **Сообщения (12.11, миграция `025`)** — разметку одного сообщения делает `message_html()` в `messages.php`: её же получает `main.js` в JSON (`message.html`), второй копии разметки в скрипте нет. У своих сообщений галочки (`.msg__ticks`; прочитано — `.is-read`). Ответ: `messages.reply_to_id`, поле `reply_to` в форме, цитата `.msg__quote[data-quote]`. Удаление своего непрочитанного — `action=unsend` → `delete_unread_message()`: текст стирается, ставятся `deleted_at` и `read_at` (удалённое не считается непрочитанным), в журнал — `message.unsend`. Опрос (`action=poll`) кроме новых сообщений отдаёт `state`: `read_upto` (до какого своего сообщения собеседник дочитал) и `deleted` (id удалённых). Письмо о новом сообщении к этому моменту могло уйти — из почты текст не отзывается.
- **Телефон продавца — только вошедшим (12.11):** `phone.php` гостю отвечает 401 и `{login}`; на странице объявления у гостя вместо кнопки — ссылка на вход с возвратом.

На странице вместо объявления — «Podrška Place4Market»; письма — шаблоны `mail.message_support_*` (пользователю) и `mail.message_reply_*` (сотруднику); журнал — `admin.message`.
- **Подача:** «Опубликовать» активна, только когда форма проходит проверку (`form.checkValidity()`); «Сохранить черновик» — всегда.

**Заголовки безопасности** — `security_headers()` (`helpers.php`), вызывается в начале обоих bootstrap, потому что OpenLiteSpeed не применяет `Header` из `.htaccess`: `Content-Security-Policy` (`CSP`: всё только со своего домена; скрипты — только файлами, встроенных нет — `<script type="application/json">` и JSON-LD это данные; `style-src 'unsafe-inline'` нужен для атрибута `style` у фото — средний цвет; `blob:` — предпросмотр фото в подаче; по HTTPS добавляется `upgrade-insecure-requests`), `X-Content-Type-Options`, `X-Frame-Options: SAMEORIGIN`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, по HTTPS — `Strict-Transport-Security` (год, без поддоменов). Новая интеграция (карты, аналитика, чат) — добавить её источник в `CSP`, иначе браузер её заблокирует. Статические файлы (картинки, CSS) идут без этих заголовков и без `X-Robots-Tag`: на OpenLiteSpeed их можно задать только отдельным `context` в настройках сайта, а он отключает для своей папки правила `.htaccess` (проверено 08.11). Кэш статики — настройка сервера `/etc/openlitespeed/httpd-expires.conf` (CSS, JS, шрифты — год, картинки — неделя; копия на случай обновления — `/usr/local/directadmin/custombuild/custom/openlitespeed/conf/`).

**Аналитика и согласие на cookies (11.11)** — Google Analytics 4, включается строкой `'analytics' => ['ga4' => 'G-…']` в `app-config.php` (`analytics_id()` в `helpers.php` проверяет формат; пусто — всё выключено). Пока ID задан:
- `partials/consent.php` (из `footer.php`) — баннер внизу слева, на телефоне над нижней панелью; виден, пока нет cookie `p4m_consent` (`granted` / `denied`, год). Фиксирован поверх страницы — ничего не сдвигает (CLS 0). В подвале, колонка «Place4Market», — кнопка «Podešavanja kolačića» (`data-consent-open`), открывает баннер снова. Тексты — `consent.*`.

Consent Mode: `analytics_storage` — granted, рекламные `ad_*` — всегда denied. «Odbijam» после согласия переключает `analytics_storage` в denied и удаляет cookies `_ga*`.

Демо-механизм (`data-toast`, `data-demo`, `data-demo-submit`, `initDemo`) удалён 03.11: все кнопки сайта и админки работают с сервером.

Фото в форме подачи готовятся в браузере сразу при добавлении (`preparePhoto()` в `main.js`), по одному, чтобы телефону хватило памяти:
- поворот по EXIF применяется, длинная сторона уменьшается до 2560 px, сохранение в JPEG 0.9 — заодно пропадают EXIF и геолокация; фото с телефона 5–12 МБ → ~1 МБ;

- прозрачный PNG ложится на белый фон; больше 30 МБ, сверх 12 штук или формат, который браузер не открывает (HEIC вне Safari), — сообщение пользователю. Прочие сбои уходят в журнал через `reportError()`.

Готовое фото сразу уходит на `photo-upload.php` (по одному, `fetch`), сервер обрабатывает его и возвращает id; форма отправляет только `photo_ids[]` в порядке плиток (первое — обложка). Пока загрузка идёт, отправка формы заблокирована. Уже загруженные фото (редактирование, форма с ошибкой) приходят в `data-photos` списка.

## SEO

Каждая страница до подключения `header.php` задаёт в `$page`: `title`, `description`, `canonical` (`[путь, параметры]` без языка), `robots`, `schema[]` (JSON-LD), `og_type`/`og`. Тег `<head>` собирает `seo_head()` из `source/inc/seo.php`. На страницах с `noindex` (служебные, выдача с поиском/фильтрами/сортировкой) canonical и hreflang не выводятся.

Выдача: индексируется только чистая категория с объявлениями (и её страницы); поиск, фильтры, сортировка и пустая категория — `noindex, follow`. Номер страницы — один адрес на страницу: `?page=1`, `0`, `abc` или дальше последней — 301 на правильный; у страниц со второй — «страница N» в title и description. Объявление без цены не выводит `Product` (без `offers` Google считает его ошибкой), его видео идут отдельными `VideoObject`.

**Карта сайта** (`sitemap.php`, `/sitemap.xml`) — индекс с частями: `?part=pages` (главная, «все объявления» — пока они есть, категории с объявлениями или со своим SEO-текстом на обоих языках, информационные), `?part=landings` (включённые посадочные с объявлениями), `?part=listings&n=N` и `?part=sellers&n=N` по 10 000 записей (`SITEMAP_SIZE`; × 3 языка = 30 000 адресов при пределе 50 000). Попадает то же, что индексируется: опубликованные объявления активных продавцов в видимых категориях (`SITEMAP_FROM` в `repo.php`). `lastmod` — `updated_at` объявления (счётчики просмотров и избранного его не меняют), у категории и продавца — самое свежее из их объявлений.

**Правила индексации, уточнённые 12.11 (аудит, `doc/AUDIT.md`):**
- Пустая страница выдачи — `noindex`, кроме чистой страницы категории, у которой есть свой SEO-текст на обоих языках (`category_has_text()`): она `index` и в карте сайта ещё до первого объявления. Посадочные без объявлений по-прежнему `noindex`.
- Объявление: title — «заголовок — категория, место» (если не помещается в ~65 знаков с названием сайта — «заголовок — категория», затем «заголовок — место», затем один заголовок); description — `meta.listing` на языке страницы (категория, место, заголовок, цена, начало описания), обрезается по границе слова (`text_cut()`). Текст пользователя не переводится, поэтому языковые версии различаются нашими словами.
- Объявление в скрытой категории видно только автору и персоналу (для остальных 404), как и объявление заблокированного продавца; в избранное оно не попадает.
- Страница продавца без опубликованных объявлений — `noindex, follow`.
- Пагинация выдачи (`pagination()`): первая, последняя и соседние с текущей страницы, остальное — «…»; в ссылках только параметры поиска (`search_query()`), метки `utm_*` не переносятся.
- `404.php` записывает свои `title` и `robots` в глобальный `$page`: его подключают и изнутри функции (`route_resolve()`).

Пока идёт разработка, сайт закрыт от индексации заголовком `X-Robots-Tag: noindex, nofollow` — в `.htaccess` и в `source/inc/bootstrap.php` (блоки `DEV-ONLY`, снять оба при запуске).

## Журнал ошибок и действий

`source/inc/log.php` подключается первым в обоих bootstrap и ловит всё, что падает дальше: предупреждения PHP, необработанные исключения, фатальные ошибки (в том числе нехватку памяти и ошибки разбора). Ошибки JS приходят из `main.js` и `admin.js` на `js-error.php`.

```php
log_event('error', 'Mail not sent', ['to' => $email]);    // уровни: debug, info, warning, error, critical
log_exception($e);                                         // пойманное исключение, с трассировкой
log_action('listing.delete', ['id' => 1048]);              // журнал действий (кто, что, над чем)
log_set_user($id, 'admin');                                // кто действует (в админке уже задан)
```

- Где лежит: таблица `log_entries` (с 31.10). Пишется **своим подключением** (`log_db()`), поэтому откат транзакции страницы запись не стирает. В записи: время (UTC, с миллисекундами), уровень, канал (`app`, `audit`, `http`, `js`, `db`, `mail`, `upload`, `cron`), сообщение, id запроса, метод и адрес, IP, пользователь и роль, браузер, контекст (JSON). Хранение 90 дней (`cron.php` удаляет старое). Защита базы: после `LOG_DB_DAILY_ROWS` (50 000) записей за сутки (UTC) пишутся только `error` и `critical`, а первая пропущенная запись заменяется одной ошибкой «Journal: daily limit … reached» (и уведомлением, если оно настроено) — так видно, что что-то засыпает журнал.
- Запасной путь: если база недоступна (или таблицы ещё нет), запись уходит в файл дня — JSON на строку (`2026-10-29.log`), на сервере в `app-logs/` рядом с `public_html`, при `php -S` — в `logs/` проекта (в `.gitignore`), другое место — `P4M_LOG_DIR`. `cron.php` переносит такие файлы в базу (`log_import_files()`: файл переименовывается, импортируется, удаляется; при сбое остаток ждёт следующего запуска). Раздел журнала показывает, сколько файлов ждёт. Если недоступна и папка — запись уходит в журнал PHP сервера.
- **Раздел журнала в админке** — `admin/logs.php`, только для админа (`is_admin()`): фильтры по уровню (этот и выше), каналу, пользователю (id или e-mail), периоду; поиск по коду ошибки (id запроса — все записи этого запроса) или тексту сообщения и адреса; по 50 записей, подробности (контекст, IP, браузер) — раскрываются. В сайдбаре и на дашборде — число ошибок за 24 часа. История объявления (`listing-edit.php`, вкладка History) и лента дашборда — это записи `audit` (`audit_entries()`, текст строки — `audit_line()`).
- **Уведомления о критичных ошибках** (`log_alert()`): каждая запись `critical` уходит письмом и/или в Telegram по `config('alerts')`. Одна и та же ошибка (сообщение + место) — не чаще раза в 15 минут (`LOG_ALERT_PAUSE`); состояние в файле `alerts.json` рядом с журналом, поэтому работает и при упавшей базе. В письме — сообщение, место, адрес, код и ссылка на журнал с этим кодом; локально письмо пишется в `logs/mail/`. Без `alerts` в настройках уведомлений нет.
- `js-error.php` принимает не больше 30 ошибок с одного IP за 10 минут (`rate_events`).
- Пароли, токены и похожие поля (`password`, `token`, `csrf`…) в контексте и в адресах заменяются на `***`; аргументы функций в трассировку не попадают.
- При фатальной ошибке недорисованная страница заменяется страницей 500 с кодом ошибки (это id запроса, он же в заголовке `X-Request-Id`): по коду запись находится в журнале. При `php -S` на странице видна сама ошибка, на проде — нет.
- 404 тоже пишутся (канал `http`): битая ссылка с нашей же страницы — `warning`, заход извне — `info`.

## Модерация и жалобы

Новое и изменённое объявление приходит в админку со статусом `pending` (счётчик в сайдбаре). Все действия персонала — POST на `admin/moderate.php` (CSRF, `back` — на какую страницу вернуться), каждое пишется в журнал действий.

- **Одобрить** (`approve_listing()`): первое одобрение — `published_at` и `sorted_at` = сейчас (наверх выдачи), `expires_at` = +30 дней (`setting('listing_days')`). Одобрение после правки — место в выдаче и срок сохраняются, срок продлевается, только если истёк (правка не даёт бесплатного «поднять»). Продавцу — письмо `mail.listing_approved`.
- **Отклонить** (`reject_listing()`): причина — ключ (`reject_reasons()` в админке, `rj.<ключ>` на языке продавца) и сообщение (`reject_comment`). Продавец видит их в профиле, письмо `mail.listing_rejected` со ссылкой на правку — если не снята галочка. Исправленное объявление снова уходит на модерацию.
- **Удалить** (`staff_delete_listing()`): как удаление автором — статус `deleted`, фото с файлами удаляются, строка остаётся для переписки.
- Массово: отметить строки в списке → «Approve» / «Reject» / «Delete» (`form[data-bulk-form]` отправляет `ids[]` отмеченных строк, диалог отклонения получает их через `data-bulk-ids`). Из меню строки, из карточки объявления и из очереди на дашборде — то же для одного.
- **Блокировка** пользователя (`block_user()`) — из карточки объявления (вкладка Seller), страницы пользователя или по жалобе.
- Письма продавцу — `notify_seller()`: на языке, на котором написано объявление (`in_lang()`), ссылки ведут на эту же языковую версию. Сбой отправки пишется в журнал и модерацию не останавливает.

Когда персонал удаляет объявление (из списка, карточки или решением по жалобе), остальные открытые жалобы на него закрываются вместе с ним (`resolve_listing_reports()`, решение `remove`, заметка «Closed with the listing», в журнале — `report.resolve` с `auto`). Диалоги админки (отклонение, разбор жалобы) при каждом открытии начинаются с пустой формы: текст, набранный для одной строки, не уйдёт другому продавцу.

Жалобы: на сайте — ссылка «Пожаловаться» на чужом опубликованном объявлении (гостя просит войти), диалог отправляет на `report.php`. Причины — ключи `r.<ключ>`, одна открытая жалоба от пользователя на объявление (повтор — та же благодарность, без новой записи), не больше 10 в час (`RATE_LIMITS['report']`). В админке (`reports.php`): «Review» → «Mark in review» или решение с внутренней заметкой. Решение действует сразу: «Ask the seller to edit» — объявление отклоняется с сообщением продавцу; «Remove» — удаляется; «Remove and block» — удаляется, продавец блокируется; «Dismiss» — ничего. Кто и как решил — в таблице жалоб.

Журнал действий: `listing.approve`, `listing.reject`, `listing.remove`, `admin.user_block`, `admin.user_unblock`, `report.create`, `report.review`, `report.resolve` (в контексте `listing_id`, `report_id`, причина или решение).

## Списки админки

Объявления, пользователи и жалобы (`listings.php`, `users.php`, `reports.php`) фильтруются и листаются на сервере: фильтры — в адресе (GET), поэтому ссылку с выборкой можно отправить коллеге, а после действия (`back`) страница возвращается с теми же фильтрами и номером страницы. По 50 строк (`ADMIN_PAGE_SIZE`), счётчики на вкладках учитывают остальные фильтры.

- Объявления: `status` (как показан: активное с истёкшим сроком — `expired`), `q` (`#1048` или `1048` — по id; иначе текст объявления в любой азбуке, имя или e-mail продавца), `cat` (родитель включает подкатегории), `city`, `user` (объявления одного продавца — ссылка из числа объявлений в списке пользователей). Очередь модерации (`pending`) — сначала старые.
- Пользователи: `tab` (`active`, `blocked`, `deleted`, `staff`), `q` (id, имя, e-mail, телефон), `role`, `city`; новые сверху.
- Жалобы: `status` (по умолчанию `open`, `all` — все), `reason`, `q` (id жалобы или объявления, текст объявления, автор жалобы).
- Запросы — `admin_listing_where()`, `admin_user_where()`, `report_where()` в `repo.php`; ссылки — `list_url()`, страница — `list_page()`, навигация — `admin_pagination()` (`inc/admin/helpers.php`). Селекты фильтра отправляют форму сразу (`form[data-autosubmit]`), без JS — кнопка «Show».
- **Экспорт CSV** (`admin/export.php?type=listings|users` + те же фильтры): UTF-8 с BOM, разделитель `;` (Excel открывает таблицей), значения, похожие на формулу (`=`, `+`, `-`, `@`), получают префикс `'` — поэтому телефоны выглядят как `'+381…`. Объявления — персонал, пользователи (личные данные) — только админ. Каждая выгрузка — `admin.export` в журнале (тип, фильтры, число строк).

## Правка объявления персоналом

`admin/listing-edit.php` принимает POST сам (CSRF), после действия — обратно на ту же вкладку:

- `save` — заголовок, описание, категория, город, цена (пусто — «по договорённости»), валюта, торг, состояние (обязательно, если оно есть у категории), способ связи («Как связаться»); сделка, вид, марка, район и «Oglašava» (с 10.11). Блоки сделки, вида и марки — у каждой подкатегории свои (`[data-for]`, как в форме подачи), район — у недвижимости в городе с районами (`[data-city]`); при смене категории или города JS (`initFacets()` в `admin.js`) показывает нужные, скрытые выключены и не отправляются. Сохранение — `clean_facets(…, false)`: что не подходит категории и городу, сбрасывается, «— Not set —» допустимо (у старых объявлений этих полей нет). Проверки — как при подаче; при ошибке форма остаётся с введённым. Это исправление, а не новая версия: статус, место в выдаче, срок и причина отказа не меняются, автору письма нет (`staff_save_listing()`). Язык текста: кириллица → `sr-cyrl`, латиница сохраняет прежний (`en` или `sr-latn`). Атрибуты категории (год, пробег…) правит автор; при смене категории остаются только те, что у неё есть.
- `photo_upload` — `photos[]`, обработка та же, что на сайте (`process_photo()`), фото добавляются в конец и записываются на автора; не больше `setting('max_photos')`; что не принято — перечислено в сообщении. `photo_cover` — фото становится обложкой, `photo_delete` — удаляется вместе с файлами (`set_listing_cover()`, `delete_listing_photo()`).
- Удалённое объявление открывается только для просмотра.
- Журнал: `listing.staff_edit` (какие поля изменились), `listing.staff_photos` (`op`: `add` / `cover` / `delete`) — видны в истории объявления и на дашборде.

## Пользователи в админке

Действия с аккаунтом — POST на `admin/user-actions.php` (CSRF, `back`), блокировка — по-прежнему `moderate.php` (одному — `user_id`, массово — `ids[]`). Строки сайта в админке подключены на английском (`i18n_use('en')` в её bootstrap), поэтому `t()` там работает; свои тексты админки — `at()`, см. «Тексты админки (EN / RU)».

| Действие | Кто | Что делает |
|---|---|---|
| `save` | админ | имя, e-mail (занятый — ошибка; ожидающая смена адреса сбрасывается), телефон (только сербский), город, роль (свою — нельзя), отметки «e-mail / телефон подтверждён» (телефон — не без номера и не номер, подтверждённый у другого) |
| `role` | админ | из меню строки: «Make moderator» / «Make regular user» |
| `note` | персонал | внутренняя заметка (`users.staff_note`, до 2000 символов) |
| `reset_link` | персонал | письмо со ссылкой сброса на языке пользователя, ссылка живёт час; заблокированному — нельзя |
| `end_sessions` | персонал | выход на всех устройствах (`end_user_sessions()`); себе — нельзя |
| `delete` | админ | как удаление владельцем (`delete_account()`): объявления и фото удаляются, личные данные стираются; аккаунты персонала пропускаются — сначала сменить роль |

Модератор видит профиль только для чтения, без экспорта и удаления. Вкладка Activity — записи журнала действий этого пользователя и о нём (`audit_entries($limit, null, $userId)`).

**Сеансы:** в сессии при входе хранится `users.session_version`; `auth_init()` выходит, если версия выросла. Её поднимают «End all sessions», смена пароля в профиле и сброс по ссылке (текущее устройство после смены пароля остаётся в системе, остальные выходят; раньше сессии других устройств переживали смену пароля — удалялись только токены «запомнить меня»).

Журнал действий: `admin.user_update` (какие поля, новая роль), `admin.user_note`, `admin.user_reset_link`, `admin.user_sessions_end`, `admin.user_delete`, `admin.export`.

## Категории в админке

`admin/categories.php` (персонал): дерево в два уровня, форма справа, POST на себя (CSRF).

- **Сохранить** — названия на трёх языках (кириллица пустая — собирается из латиницы через `sr_cyr()`), slug (один на все языки, латиница, цифры и дефисы; при правке существующей категории JS его не трогает — это адрес, его смена ломает старые ссылки и сохранённые поиски), родитель (только верхнего уровня; категория с подкатегориями остаётся наверху), иконка (только у верхнего уровня, `category_icon_names()`), порядок, видимость.
- **SEO-тексты** — `h1_*`, `seo_title_*`, `meta_*`, `text_*` (`en` и `sr`; кириллическая страница получает сербский текст в кириллице). Пусто — h1 по названию, шаблоны title и description (см. «Тексты (этап C)»), без SEO-текста. В title и description работает `{count}`, у полей — счётчик знаков. SEO-текст — абзацы через пустую строку (`clean_text_block()`: до `SEO_TEXT_MAX` = 5000 знаков, лишние пустые строки убираются). Используются только на чистой странице категории (с поиском — общий заголовок). В SEO-тексте можно ставить ссылки `[слова](/oglasi/…)` (подсказка под полем; правила — «Ссылки в SEO-тексте»). Вывод — `category_seo()`, `category_h1()`, `seo_text_html()` в `site.php`.
- **Видимость** — переключатель в строке дерева. Скрытая категория (или её родитель): нет в меню, на главной, в подвале, в форме подачи и в карте сайта, страница — 404, объявления уходят из выдачи и поиска (`CATEGORY_VISIBLE` в `listing_search_where()` и `sitemap_listings()`); прямая ссылка на объявление работает. Сайт берёт список из `visible_categories()`, админка — из `categories()` (со всеми, скрытые помечены «(hidden)» в фильтрах).
- **Удалить** — только без подкатегорий и объявлений в любом статусе (удалённые хранятся для истории); иначе — скрыть.
- Журнал: `admin.category_create`, `admin.category_update` (какие поля, старый slug), `admin.category_hide`, `admin.category_show`, `admin.category_delete`.

## Тексты админки (EN / RU)

Админка на двух языках — английском и русском (пожелание заказчика, 10.11). Тексты — свои словари `source/lang/admin/en.php` (источник ключей) и `ru.php` (те же ключи; чего нет в русском — берётся английский), функции `at('key', [params])` и `atp('key', $n)` (`source/inc/admin/i18n.php`). Сайтовая `t()` в админке остаётся английской: через неё идут письма продавцам на их языке (`in_lang()`), тексты админки через неё не пускаем. Множественное число — `plural_form($n, $lang)` (у русского формы как у сербского: `one` / `few` / `many`).

- **Язык — в профиле:** `users.admin_lang` (миграция `018_admin_lang`, по умолчанию `ru`), поэтому один и тот же на всех устройствах. Переключатель — кнопка с глобусом в шапке (предлагает другой язык: «EN» / «RU»), POST на `admin/lang.php` (CSRF), возврат на ту же страницу, в журнал — `account.admin_lang`. До входа (страница входа) — русский. В профиле сотрудника (`user.php`) язык админки виден рядом с языком писем.
- **Что переводится:** весь интерфейс — меню, страницы, формы, подсказки, сообщения после действий (`flash`), диалоги, статусы (`status_meta()`), роли (`role_name()`), причины отказа и жалоб, решения по жалобам, строки истории и дашборда (`audit_line()`: ключи `audit.*`, имена полей — `field_labels()`), заголовки CSV. JS берёт подписи из разметки: кнопка «Подтвердить» — `data-label` в `footer.php`, показ пароля — `data-label-show` / `data-label-hide`.
- **Что остаётся как есть:** названия категорий, видов и марок — английские (решение 10.11); данные пользователей (заголовки объявлений, имена, комментарии); технические сообщения журнала (`log_event()`), названия каналов и уровней; термины SEO title / Meta description / H1. Заметка «закрыта вместе с объявлением» в жалобе пишется на языке того, кто удалил.
- **Новый текст в админке** — только через `at()`: ключ в оба словаря (группы по страницам: `nav`, `common`, `list`, `edit`, `rep`, `users`, `user`, `inbox`, `cat`, `land`, `set`, `logs`, `mig`, `csv`, `audit`, `field`, `status` …). Проверка, что ключи совпадают: `php -r '$en=require "source/lang/admin/en.php"; $ru=require "source/lang/admin/ru.php"; var_dump(array_diff_key($en,$ru), array_diff_key($ru,$en));'`.

## Хранилище и расходы

`admin/usage.php` (только админ, 12.11; логика — `source/inc/usage.php`, миграция `033`). Глобального потолка SMS на сайт нет (решение 12.11, только лимиты на аккаунт, номер и IP в `RATE_LIMITS`), поэтому расходы смотрим здесь.

- **Место на диске** — `usage_refresh()` обходит папки загрузок (`uploads/listings`, `uploads/avatars`: одна папка — одно фото, видео или фото профиля), при подключённом облаке — ключи бакета (`s3_objects()`, `storage.php`), очередь видео, файлы журнала и сессий, спрашивает у базы её размер (`db_size()`). Обычный PHP, без `du`: веб-PHP не запускает программы, а `open_basedir` пускает в `/home/placemar/`. Запускает `cron.php` раз в час и кнопка «Пересчитать сейчас». Итог — строка в `storage_snapshots` на сутки (UTC), перезаписывается до конца дня: страница берёт последнюю, график «по дням» — историю (90 дней; фото, видео, всё остальное). Плашка, когда диск занят от `DISK_WARN_PERCENT` (85 %).
- **Бесхозные файлы** — папка загрузок, на которую не ссылается ни `listing_photos`, ни `listing_videos`, ни `users.avatar` (на диске или в облаке); файл очереди видео без своей строки; рабочая папка обработчика видео, оставшаяся после сбоя. Удалить — галочками или «Удалить все» (POST, CSRF, подтверждение): каждый объект перед удалением проверяется заново (`usage_orphan()`), моложе `USAGE_ORPHAN_HOURS` (24 ч) не трогаем — это может быть загрузка в процессе. В журнал — `admin.storage_cleanup` (сколько, объём, первые 20 путей). Копия удалённого ещё 14 дней лежит в бэкапах. Обратный случай — строка в базе, а папки нет — только показываем (ссылка на объявление или пользователя): это ошибка, а не мусор. Брошенные загрузки (фото или видео без объявления) удаляет сам `cron.php` через сутки, здесь видно, сколько их ждёт.
- **Бэкапы** — последняя запись `p4m-backup` в журнале (канал `backup`): время, дамп базы, все копии; «запаздывает», если успешной копии больше 36 часов, «сбой» — если последняя запись `Backup failed` (с шагом).
- **SMS** — свой счёт по журналу: `code.sent` и `code.confirmed` (с 12.11, `code_confirm()`) с `channel = sms`, по дням (`sms_counts_by_day()`), за сегодня, 7 и 30 дней и месяц; оценка — `SMS_PRICE_USD` ($0,41 за SMS в Сербию) и `SMS_CHECK_PRICE_USD` ($0,05 за подтверждённый код, Verify) из `codes.php`. Журнал хранится 90 дней — дальше история только у Twilio.
- **Баланс и счёт Twilio** — `sms_billing()`: Balance API и Usage Records (`ThisMonth` / `LastMonth`, категория `totalprice` — всё, что списано с аккаунта, он только шлёт коды), ключи — те же `api_key` / `api_secret` из `config('sms')`, нужен ещё `account_sid`. Ответ хранится 10 минут в настройке `sms_billing_info` (JSON, в форме настроек её нет), кнопка «Запросить Twilio» — сразу. Не ответил — остаются прежние цифры с датой, сбой — журнал, канал `sms`. Без драйвера `twilio` — плашка «SMS не подключены».

## Избранное и сохранённые поиски

- **Избранное** (`favorites`): сердечко отправляет `favorite.php` (POST `id`, `on`, csrf из JSON в `footer.php`). Сохранить можно только опубликованное, убрать — всегда; `listings.favorites_count` меняется вместе с этим. Не больше 300 в час (`RATE_LIMITS['favorite']`). На странице избранного — только ещё опубликованные (`favorite_listings()`).
- **Сохранённые поиски** (`saved_searches`): кнопка «Сохранить поиск» на выдаче — форма на `saved-search.php` с текущими фильтрами (гостю — ссылка на вход, уже сохранённый — ссылка «Поиск сохранён» в избранное). Хранятся параметры адреса без сортировки (`saved_search_params()`), по ним же ищутся повторы; до 20 на пользователя. Название строится из фильтров на языке страницы (`search_label()`), не хранится.
- «N новых» — объявления, опубликованные (`published_at`) после сохранения или последнего открытия; открытие идёт через `saved-search.php?open=id` (ставит `seen_at`).
- **Оповещения на почту** — `cron.php`: поиски с включёнными оповещениями проверяются не чаще раза в сутки (`checked_at`), одно письмо `mail.search_alert` на пользователя со всеми поисками, где есть новое, на языке из профиля (`users.lang`; если его нет — на языке последнего сохранённого поиска). Только активным пользователям с подтверждённой почтой. Включение оповещений отсчитывает новое с этого момента. Не ушло письмо — поиски проверятся в следующий запуск.
- **Снижение цены** — в избранном хранится цена и валюта на момент сохранения (`favorites.price`, `currency`). `cron.php` раз в час находит опубликованные объявления, которые стали дешевле в той же валюте (смена курса EUR в настройках снижением не считается), и шлёт одно письмо `mail.price_drop` на пользователя со всеми такими объявлениями («было → стало», ссылка), если в профиле включено «снижение цены» и почта подтверждена (как у оповещений поисков и сообщений); после письма цена запоминается заново (`price_drops()`, `remember_favorite_prices()`). Подорожание и смена валюты тоже запоминаются молча — следующее снижение считается от новой цены. До 300 пользователей за запуск.
- Фильтры выдачи читает `search_filters()` (`site.php`), ссылки строит `search_query()`, подписи фильтров — `search_filter_labels()`: одни и те же для `category.php`, сохранённых поисков и писем.

## Сообщения

- Диалог — один на объявление и покупателя (`conversations`), продавец — автор объявления. «Написать продавцу» ведёт на `messages.php?listing=id`: открывается диалог покупателя об этом объявлении, а если его нет — пустая ветка; сам диалог создаётся первым сообщением (`start_conversation()`, `listings.messages_count` считает диалоги). Новый диалог — только по опубликованному чужому объявлению активного продавца; в существующем можно писать и после снятия объявления, пока собеседник не заблокирован.
- Отправка, прочтение, новые сообщения и удаление — POST на `messages.php` (`action` = `send` / `read` / `poll` / `delete`, csrf); `main.js` получает JSON, без JS форма возвращает на ветку. Сообщение до 2000 символов, язык определяется по тексту (`detect_text_lang()`), показывается через `user_text()`. Лимиты: 100 сообщений в час, 30 новых диалогов в сутки (`RATE_LIMITS`).
- Прочтение: `?c=id` отмечает ветку прочитанной до вывода шапки; ветку, открытую в браузере, отмечает `main.js` (на телефоне — только когда она действительно открыта, а не стоит за списком).
- Удаление — только у себя (`buyer_hidden_at` / `seller_hidden_at`): диалог скрывается и считается прочитанным, у собеседника остаётся всё. Новое сообщение возвращает диалог, но только с сообщениями после удаления.
- Письмо получателю `mail.message_new` — на первое непрочитанное в диалоге, дальше не пишем, пока он не прочитает. Только активным с подтверждённой почтой и включённым «сообщения» в профиле; язык — из профиля получателя (`users.lang`), если его нет — тот, на котором он пишет в этом диалоге (продавцу до ответа — язык объявления). Сбой письма пишется в журнал и отправку не останавливает.
- Новые сообщения без перезагрузки: открытая ветка раз в 10 секунд спрашивает `poll` (`after` — id последнего показанного, `data-msg` у каждого сообщения), пока вкладка видима, и сразу при возвращении на неё; пришедшие отмечаются прочитанными, счётчики в шапке обновляются. Свои сообщения не дублируются (у ответа `send` тоже есть id).
- Быстрые ответы («Ещё продаётся?», «Торг уместен?»…) — вопросы покупателя, поэтому продавцу в диалоге о его объявлении они не показываются.
- Фото в сообщениях нет (кнопка-скрепка убрана 03.11) — при необходимости отдельной задачей.

## Фото объявлений

Правила (размеры, качество, обработка) — в `CLAUDE.md`, раздел 2. У объявления в `images` лежит список фото, первое — обложка:

```php
['path' => 'img/demo/1048-1', 'color' => '#938e85', 'sizes' => [1920 => [1920, 1280], 960 => [960, 640], 480 => [480, 320], 320 => [320, 213], 200 => [200, 133]]]
```

Файлы — `source/<path>/<размер>.webp`, размер = длинная сторона. Выводит их `photo($photo, $sizes, $opts)` (`helpers.php`, общий для сайта и админки):
- размеры: 1920 / 960 / 480 / 320 / 200 (320 — карточки на обычных экранах); в `srcset` все размеры (или до `max`), `width`/`height` для пропорций, средний цвет фоном до загрузки — CLS 0;
- `sizes` по месту — `PHOTO_SIZES` в `site.php` (карточка, галерея, миниатюра, строка, чат), потолок размера — `PHOTO_MAX`; в галерее фото вписывается целиком (`pic--contain`), `photo_sizes_contain()` уменьшает `sizes` для вертикальных;
- `lazy` по умолчанию; у первых четырёх карточек выдачи и главной — без него (`$cardEager`), у первой и у главного фото объявления — `fetchpriority="high"` (`$cardPriority`, `priority`).

На странице объявления обложка уходит в `og:image`, все фото — в `Product.image`. Без фото выводится заглушка с иконкой категории (`placeholder()`).

Видео (`videos` у объявления: `id`, `path`, `file`, `width`, `height`, `duration`, `bytes`, `poster` — фото того же вида) встаёт в галерею вторым слайдом, после обложки. Показываются только готовые (`status = ready`); загрузка пользователями — раздел «Видео объявлений» ниже.
- фасад `button[data-video]`: постер через `photo()`, кнопка и длительность (`video_time()`); `<video>` создаётся только по нажатию (`initVideos()` в `main.js`), до этого грузится лишь постер, и только когда слайд открыт;
- при переходе на другой слайд ролик ставится на паузу, стрелки и свайп на плеере не листают галерею; ошибки файла или кодека уходят в журнал;
- в `Product` — `subjectOf` с `VideoObject` (постер, файл, длительность).

### Хранение: диск или облако (`source/inc/storage.php`, 11.11)

Загруженные файлы лежат на диске сервера (`uploads/listings/ГГГГ/ММ/<случайное>/`) или в S3-совместимом облаке — Cloudflare R2, Amazon S3, Backblaze B2, Hetzner, MinIO. Переключатель — `'storage'` в `app-config.php` (пример — шапка `storage.php`; без него — диск, как раньше):
- **Путь в базе говорит, где файл:** `uploads/listings/…` — на диске, `cloud:uploads/listings/…` — тот же ключ в бакете. Поэтому старые и новые фото живут рядом, схема не менялась, а возврат драйвера на `local` меняет только место новых загрузок. Адрес строит `storage_file_url()` (через `photo_url()` / `video_url()`): облачный — `public_url` + ключ; `site_url()` абсолютный адрес не трогает (`og:image`, JSON-LD).
- **Загрузка:** `process_photo()` пишет размеры в локальную папку, `storage_save_folder()` отправляет их в бакет (`Content-Type`, `Cache-Control: public, max-age=31536000, immutable`) и удаляет локальную копию. Облако не ответило — фото остаётся на диске, загрузка у пользователя проходит, в журнале `warning` (канал `storage`).
- **Удаление:** `delete_photo_files()` → `storage_delete_folder()`: локальная папка или все ключи под префиксом (ListObjectsV2 + DELETE). Демо-фото (`source/img/demo`) не удаляются никогда.
- **Запросы к S3:** path-style (`<endpoint>/<bucket>/<key>`), Signature V4 на чистом PHP (`s3_sign()`, проверена на четырёх примерах из документации AWS), curl; ключи доступа в журнал не пишутся.
- **CSP:** домен `public_url` добавляется в `img-src` и `media-src` сайта и админки (`csp()` в `helpers.php`).
- **Перенос уже загруженного:** `php source/db/storage-move.php --dry-run` (сколько папок и мегабайт) → `php source/db/storage-move.php [--limit=N]`: по папке — загрузить, сверить размер каждого файла в бакете, сменить путь на `cloud:…` (`listing_photos`, `listing_videos`), удалить локальную копию; сбой — папка остаётся на диске, повторный запуск продолжает.
- **Включение (когда решит заказчик), для R2:** бакет → API-токен «Object Read & Write» на этот бакет (Access Key ID, Secret) → свой домен для раздачи (например `media.place4market.com`, через Cloudflare) → `'storage'` в `app-config.php` на сервере → проверить загрузку фото → `storage-move.php`. Бэкап `p4m-backup` снимает только `uploads/` на диске: файлы в облаке бэкапит само облако (версии / репликация бакета) — решить при включении.
- Проверено 11.11 на локальной заглушке S3, которая сверяет подпись и хеш каждого запроса: загрузка в бакет (5 размеров, тип, кэш), публичный адрес, удаление, отказ облака (фото на диске + `warning`), перенос 3 папок (`--dry-run`, повтор), вывод на странице объявления и в выдаче, `og:image`, CSP сайта и админки. Без `'storage'` сайт работает как прежде.

### Загрузка и обработка (`source/inc/media.php`)

- **Фото профиля** (миграция `028`, `users.avatar`): нажатие на аватар в профиле → `initAvatar()` в `main.js` вырезает средний квадрат до 640 px → `photo-upload.php` с `purpose=avatar` → `process_avatar()`: те же проверки, что у фото объявлений (`photo_load()`), квадраты 320 и 96 WebP в `uploads/avatars/ГГГГ/ММ/<случайное>/` (или в облаке), прежнее фото удаляется. Вывод — `avatar($user, $size)` (`site.php`): фото или инициалы. Убрать: «Ukloni fotografiju» в профиле, «Удалить фото профиля» в карточке пользователя в админке (`avatar_remove`); при удалении аккаунта файлы удаляются.
- Фото загружается до отправки формы и ждёт её без объявления (`listing_id` NULL, владелец — `user_id`); неиспользованные удаляются через сутки (`take_stale_photos()`: `source/db/cron.php` и изредка при загрузке, как запасной путь). При сохранении объявления `set_listing_photos()` ставит фото в нужном порядке, снятые удаляются вместе с файлами.
- Проверки: тип по содержимому (JPEG, PNG, WebP), до 15 МБ, до 16 Мп, не меньше 200 px по короткой стороне; JPEG поворачивается по EXIF; прозрачность — на белом; метаданные не переносятся (файл перекодируется).
- Размеры 1920 / 960 / 480 / 320 / 200 с качеством из CLAUDE.md, без увеличения: фото меньше 1920 хранит свой размер как самый крупный. Файлы — `uploads/listings/ГГГГ/ММ/<случайное>/<размер>.webp`, путь в БД от корня сайта (демо — `source/img/demo/…`).
- Сейчас — PHP GD, сразу при загрузке (браузер присылает ≤ 2560 px, это около секунды). На сервере есть libvips и ffmpeg, но веб-PHP запускать программы не может (`exec`, `proc_open` закрыты в DirectAdmin; в консоли открыты), поэтому переход на libvips — вместе с очередью и фоновым обработчиком из консоли: меняется `process_photo()`, остальной код нет. Видео — тем же обработчиком (ffmpeg).
- Лимиты PHP на сервере (DirectAdmin → PHP Settings домена; по замеру 12.11 — 64M / 64M / 128M): `upload_max_filesize` ≥ 16M, `post_max_size` ≥ 20M, `memory_limit` ≥ 256M (на время обработки фото `process_photo()` сам поднимает его до `PHOTO_MEMORY`, 384M: 16 Мп в GD — около 160 МБ; запрос больше `post_max_size` отвечает «слишком большой файл» и пишется в журнал). Локально: `php -d upload_max_filesize=16M -d post_max_size=20M -S localhost:8000`.

### Видео объявлений (D8, H6, 12.11; `source/inc/video.php`, миграция `032`)

- **Правила** — CLAUDE.md, раздел 2: до 60 с (`VIDEO_MAX_SECONDS`, запас 1,5 с), до 300 МБ (`VIDEO_MAX_BYTES`); MP4 H.264, 720 по короткой стороне без увеличения, CRF 28 с потолком 1,2 Мбит/с (с 12.11, решение пользователя: минута ≈ 9 МБ), не больше 30 кадров/с, AAC 96k, `faststart`, без метаданных; постер — кадр 1-й секунды через `process_photo()`. Сколько видео в объявлении — настройка `max_videos` (админка → Настройки, 1 по умолчанию, 0 — выключено).
- **Сжатие на устройстве** (12.11, `compressVideo()` в `main.js`): сервер принимает быстро (входящий канал ~240 МБ/с, OpenLiteSpeed — до 2 ГБ на запрос), узкое место — выгрузка с телефона (минута — 100–300 МБ, на 4G 1,5–4 минуты). Поэтому браузер сам пережимает ролик до отправки: WebCodecs (аппаратный кодек телефона) через библиотеку Mediabunny 1.62.1 (MPL-2.0) — `source/js/vendor/mediabunny.min.js` (только нужные части, 441 КБ / 113 КБ gzip; команда сборки — в первой строке файла, лицензия рядом), грузится только при выборе видео, на PageSpeed не влияет. 720 по короткой стороне, H.264 2,5 Мбит/с, ключевой кадр раз в 2 с, до 30 кадров/с, звук AAC, без метаданных (геометка телефона не уходит с устройства). Поворот телефона учитывается. На экране «Priprema N %», затем «Otpremanje N %». Исходник уходит, если браузер не умеет (нет `VideoEncoder`: старый Safari / Firefox на Android), не может разобрать кодек или звук, результат не меньше 90 % исходника или сжатие идёт медленнее ~150 с на ролик (слабый телефон без аппаратного кодека); сбой — `reportError()` в журнал (канал `js`). Сервер всё равно пережимает (знак, метаданные, проверка): файлу из браузера не доверяем. Замер 12.11 (Chrome на Mac): 105 МБ 1080p 50 с → 16,5 МБ за 5 с → после сервера 7,9 МБ; HEVC MOV с поворотом и геометкой 25,8 МБ → 6,3 МБ, 720×1280, геометки нет.
- **Загрузка частями** (`video-upload.php`, `main.js`): у PHP на сервере лимит 64 МБ, поэтому файл идёт кусками по 8 МБ (`VIDEO_CHUNK`), по 3 одновременно (`VIDEO_PARALLEL` в `main.js`): `start` (размер, длина из браузера) → `part` (номер куска; каждый — свой файл `<имя>.part.000`, `.001`…; размер куска проверяется; повтор после обрыва связи просто перезаписывает кусок, до 4 повторов) → `finish` (куски склеиваются под блокировкой — `video_join_parts()`; нет куска — 409 `missing`, браузер повторяет раз; затем тип по содержимому, длина из заголовка MP4 / MOV — `video_header_seconds()`) → статус `queued`. Сессия в `video-upload.php` сразу закрывается (`session_write_close()`): иначе PHP выполнял бы куски одного пользователя по очереди. Куски копятся в `VIDEO_QUEUE_DIR` вне `public_html` (`app-queue/video/` рядом с ним; локально `temp/video-queue/`; другое место — `P4M_QUEUE_DIR`). Лимит — 10 видео в сутки на аккаунт (`RATE_LIMITS['video_upload']`). Браузер сам отсекает слишком длинные файлы до отправки, слишком большие — после сжатия (большой исходник может уложиться в лимит после сжатия). Удалить видео можно и во время сжатия или отправки: всё останавливается, на сервере строка и куски удаляются.
- **Обработка** — `source/db/media-worker.php` (веб-PHP программы не запускает): cron пользователя `placemar` **каждую минуту**, один обработчик за раз (lock-файл в очереди), берёт задачи ~50 с, начатое доделывает. `ffprobe` (размер с учётом поворота телефона, длина) → `ffmpeg` под `nice`. Файл пользователя ffmpeg и ffprobe открывают только с явным разборщиком по проверенному типу (`VIDEO_TYPES`: MP4/MOV/3GP → `mov`, WebM/MKV → `matroska`) и `-protocol_whitelist file` (`video_input()`): «видео», которое на деле плейлист, не заставит ffmpeg читать файлы сервера в 2 потока → постер → папка `uploads/listings/ГГГГ/ММ/<случайное>/` с `video.mp4` и размерами постера (или облако, `storage.php`) → `ready`. Файл пользователя не годится (не видео, длиннее минуты, меньше 200 px) — сразу `failed` с причиной; наш сбой (ffmpeg, диск) — ещё попытка, всего `VIDEO_ATTEMPTS` = 3. Зависшую больше часа задачу берёт следующий запуск; зависшую на последней попытке — помечает неудачной. Руками: `php source/db/media-worker.php -v`. Пути к программам — `config('video')` (`['ffmpeg' => …, 'ffprobe' => …]`), без него — `/usr/bin`, `/usr/local/bin`, `/opt/homebrew/bin`.
- **Форма подачи**: блок «Video» под фото — кнопка, процент сжатия, процент отправки, «Obrada videa…», затем постер с длительностью; статус спрашивается раз в 5 с. Объявление можно сохранить, пока видео обрабатывается; на сайте оно появится, когда будет готово. Удалить: ещё не в объявлении — сразу (`cancel`), уже в объявлении — при сохранении формы (`set_listing_videos()`).
- **Админка**: в карточке объявления, вкладка «Фото», — видео с кнопкой удаления и строка «Видео в обработке: N».
- **Чистка** (`cron.php`): не попавшие в объявление и неудачные — через сутки (`take_stale_videos()`); файлы очереди без строки в базе — через сутки. Удаление объявления и аккаунта удаляет и папки видео.
- **Журнал**: канал `video` — `Video processed` (длина, размер, байты до и после, время), `Video rejected` (причина), `Video processing failed` (последние строки ffmpeg; последняя попытка — `error`); действия — `video.upload_started`, `video.uploaded`.
- Проверено локально 12.11 (ffmpeg 9.0; на сервере 7.1.5 — использованы только `scale` и `overlay`): вертикальный ролик с меткой поворота → 720×1280, HEVC из MOV (как у iPhone), ролик 70 с и «не видео» отклонены, 23 МБ тремя кусками через форму → 3,3 МБ за ~4 с, постер и знак на месте, удаление из объявления стирает файлы, чистка брошенных, 360 px без горизонтального скролла, админка.

### Подача и редактирование (`post.php`)

- Только для вошедших; `?id=` — своё объявление (чужое — 404). Новое и изменённое объявление уходят на модерацию (`pending`), в поиске и у гостей его нет; автор и модераторы видят его со штампом «не опубликовано» (`noindex`).
- Проверки: подкатегория внутри категории, заголовок 3–80, описание 10–3000, состояние, цена или «по договорённости», город, способ связи, до `setting('max_photos')` своих фото (12 по умолчанию) и `setting('max_videos')` видео, согласие с условиями. Публикация сразу или модерация — по настройкам (раздел «Настройки»), стоп-слово всегда отправляет на модерацию с пометкой (`moderation_note`). Язык текста определяется сам (`detect_text_lang()`): кириллица → `sr-cyrl`, č/ć/ž/š/đ → `sr-latn`, иначе по языку страницы.
- **Как связаться (D6, 12.11):** своего телефона у объявления больше нет (столбцы `phone`, `show_phone` остались для прежнего кода, удалить позже). Автор выбирает «samo poruke / samo pozivi / poruke i pozivi» (`listings.contact`); звонки — только на подтверждённый номер из профиля, без него эти варианты недоступны. `listing_contact()` (`site.php`) решает, что видит покупатель: без подтверждённого номера у продавца объявление откатывается на сообщения. «Только звонки» — кнопки «Napiši» нет, новую переписку `messages.php` не начинает (по ссылке — назад на объявление с пояснением, POST — 403). Журнал действий: `listing.create`, `listing.update`, `listing.draft`.
- **Черновик** (кнопка `action=draft`, `formnovalidate`; только у нового объявления и у черновика): обязательна лишь подкатегория, остальное сохраняется, если верно. После сохранения форма открывается снова (`?id=`); отправка черновика — обычная подача.
- **Характеристики** (`source/inc/attrs.php`): набор полей по подкатегории в `CATEGORY_ATTRS`, типы полей — `attr_fields()` (число с единицей и пределами, список, короткий текст). Все необязательные. В форме выводятся все наборы, `main.js` показывает набор выбранной подкатегории, остальные `disabled` и не отправляются. Там же — где «состояние» не спрашивается (недвижимость, услуги, работа). В БД (`attrs`, JSON) — сырые значения (`168000`, `v.diesel`); на странице объявления `listing_details()` выводит состояние и характеристики с единицами и переводом. Новое поле: ключ в `attr_fields()` и подкатегории + `a.<ключ>` и `v.<вариант>` в языковых файлах.

### Статусы и «Мои объявления» (`profile.php`)

- `draft` → `pending` (модерация) → `active` / `rejected`; `active` ↔ `inactive` (автор снял / вернул); `active` / `inactive` / `expired` → `sold` (автор нажал «Prodato», миграция `027`, `sell_listing()`): с сайта снято, не правится, в «Мои объявления» — фильтр «Završeni» с датой (`sold_at`), в шапке профиля — число проданных и сумма их цен по каждой валюте отдельно; «Aktiviraj» возвращает в `active` (срок прежний); `active` → `expired` по `expires_at` (`setting('listing_days')`, 30 с одобрения); `deleted` — удалено автором: строка остаётся для переписки и админки, фото удаляются вместе с файлами, избранное очищается. Удалённое видят только модераторы.
- Опубликовано = `LISTING_LIVE` (`active` и срок не истёк): по нему строятся выдача, карта сайта, избранное. Активное с истёкшим сроком сразу читается как `expired` (`listing_from_row()`), `cron.php` потом исправляет статус в БД.
- Порядок выдачи «Новые» — `sorted_at`: время публикации, «Поднять» переносит его на «сейчас» (не чаще раза в `setting('raise_hours')` = 24 ч, пока нельзя — кнопки нет). Продление истёкшего — ещё `listing_days` и наверх.
- Действия — POST на `profile.php` (`id`, `action` = `raise` / `deactivate` / `activate` / `renew` / `delete`, CSRF), функции в `repo.php` меняют только своё объявление в нужном статусе. Журнал действий: `listing.<action>`.

Демо-фото и демо-видео — бесплатные с Pexels, обработаны так же, как обрабатывает сервер; списки и скрипт — локально в `doc/tools/demo-photos.py`. Ими пользуются `seed.php` и `demo-listings.php` (пути `source/img/demo/…` в базе); `demo-photos.php`, `demo-videos.php` и `source/img/demo/` удаляются при чистке базы перед запуском (этап 7).

## Ассеты и кэш

CSS, JS и иконки подключаются через `asset('css/site.css')` → `source/css/site.css?v=<дата изменения>`, поэтому их можно кэшировать на год. Шрифты подключаются без версии: изменённый шрифт кладём под новым именем.

CSS и JS минифицируются при деплое (esbuild в `.github/workflows/deploy.yml`), в репозитории лежат читаемые исходники. Локально (`php -S`) работают исходники как есть.

## Адаптив

Сайт: десктоп ≥1440 (базовые стили), ноутбук ≤1439, планшет ≤1023, телефон ≤767; телефон рисуется под 360 и держится до 320. Админка: десктоп ≥1024 и мобильный ≤1023.

Сенсорные экраны (`@media (pointer: coarse)`): зона нажатия не меньше 44×44. У текстовых ссылок вне абзацев (хлебные крошки, имя продавца, заголовки в списках, ссылки и числа в таблицах админки) она невидимая — `::after` по центру ссылки размером `max(100%, 44px)`, поэтому вёрстка не сдвигается; у чекбокса строки в таблице админки переключает вся ячейка. Колонка действий таблиц админки закреплена у правого края (`position: sticky`): меню строки видно, когда широкая таблица прокручивается вбок. Горизонтальные ленты (миниатюры галереи, меню информационных страниц — `data-strip`) прокручиваются к нужному пункту сами, страница при этом не прыгает (`revealInStrip()` в `main.js`).

## Цвета и шрифты

`source/css/variables.css`: терракота `--color-accent`, олива `--color-olive`, морской `--color-sea`, бумажный фон `--color-bg`. Шрифты Lora (заголовки, цены) и Source Sans 3 (текст), обе с кириллицей, лежат в `source/fonts/` (`@font-face` в начале `variables.css`, Google Fonts не используется). Браузер грузит только нужные наборы символов; запасные шрифты подогнаны по метрикам, чтобы при загрузке ничего не прыгало. Для текста на светлом фоне используется `--color-accent-ink` (контраст AA), основной терракотовый — для кнопок с белым текстом.
